# Ядро — спецификация модулей (этап 1, изменения этапа 2)

Расположение кода: `app/lib/core/`.
Общая архитектура: `docs/architecture.md`.

---

## 0. Цель этапа 1

Работающее и полностью протестированное ядро на чистом Dart: от списка файлов до плана уборки, выполнения и отката.

**Входит в этап:**
- доменная модель и порты;
- все модули пайплайна;
- тестовая инфраструктура (фейковая файловая система);
- реализация репозиториев на drift (локальная SQLite).

**Не входит в этап:** UI (кроме пустого каркаса приложения), нативный код Android / iOS, desktop-адаптер файловой системы, ИИ, бэкенд, подписка.

**Результат этапа:** сценарные тесты на фейковой ФС проходят, включая сбои посреди уборки и откат с конфликтами.

---

## 1. Принципы ядра

1. **Логические пути.** Внутри источника файл адресуется относительным путём с разделителем `/` (например, `Download/scan.pdf`). Адаптер переводит логический путь в реальный (`C:\...`, `content://...`, идентификатор фото). Ядро ничего не знает о реальных путях.
2. **Операции только внутри одного источника.** Файл никогда не перемещается между источниками.
3. **Возможности источника определяют допустимые операции.** Например, источник «Фото iOS» не умеет перемещать файлы, но умеет добавлять в альбом. Планировщик учитывает это.
4. **В портах нет метода удаления произвольного файла.** Единственное удаление — очистка карантина, и оно принимает только ссылку на карантинный объект.
5. **Время и идентификаторы — через порты** (`Clock`, `IdGenerator`), чтобы тесты были детерминированными.
6. **Ошибки — типизированные результаты** (sealed-классы), а не исключения через границы портов.
7. **Долгие операции** отдают поток событий прогресса и поддерживают отмену.
8. **Ядро не зависит от платформы:** импортирует только стандартные библиотеки Dart без `dart:io` и чистые пакеты. Никаких Flutter, drift, платформенных пакетов.

## 2. Доменная модель (`core/model/`)

Общие правила модели:
- Все модели неизменяемые (`@immutable`), с равенством по значению. Списки внутри моделей неизменяемые.
- Конструкторы проверяют инварианты и бросают `ArgumentError` при нарушении (это ошибка программы, а не результат операции). Недопустимая смена статуса бросает `StateError`.
- Все даты хранятся в UTC (конструкторы нормализуют).
- Идентификаторы `SourceId`, `ScanId`, `SessionId`, `OperationId` — отдельные типы (extension types над строкой), их нельзя перепутать.
- Публичный вход: `core/model/model.dart`.

### LogicalPath — логический путь
Путь внутри источника относительно его корня, разделитель `/`. Пустой путь — корень источника (`LogicalPath.root`).

Запрещены: ведущий и завершающий `/`, пустые сегменты, сегменты `.` и `..`, символ NUL. Поэтому логический путь **не может указывать за пределы источника**.

Операции: `segments`, `name`, `extension` (в нижнем регистре, без точки; у `.bashrc` расширения нет, у `a.tar.gz` — `gz`), `stem` (имя без расширения), `parent`, `join`, `child`, `isWithin`, `isSameOrWithin`. Сравнение и сортировка — по кодовым единицам строки, без учёта локали. Равенство учитывает регистр.

### Source — источник
| Поле | Описание |
|---|---|
| `id` | Идентификатор (`SourceId`) |
| `kind` | `desktopFolder`, `androidFullStorage`, `androidSafTree`, `androidMediaStore`, `iosPhotos`, `iosFolder` |
| `displayName` | Имя для UI |
| `location` | Где источник находится — непрозрачная строка адаптера: корень тома при полном доступе к хранилищу Android и для папки desktop, позже — URI дерева SAF или закладка iOS. Ядро её не читает. Пусто у источников, перенесённых из схемы БД версии 1 (место неизвестно — источник добавляется заново) |
| `capabilities` | `SourceCapabilities`: флаги `canMove`, `canMkdir`, `canQuarantine`, `quarantineRestorable`, `canAddToAlbum`, `providesCapturedAt`, `systemPurgesQuarantine` (карантин — системная корзина, которая очищается сама, как на Android) |
| `enabled` | Участвует ли в уборке |

### FileEntry — файл в индексе
| Поле | Описание |
|---|---|
| `sourceId` | Источник |
| `path` | Логический путь внутри источника (не корень) |
| `name`, `extension` | Имя и расширение (в нижнем регистре). **Вычисляются из `path`**, отдельно не хранятся |
| `size` | Размер в байтах (≥ 0) |
| `modifiedAt` | Дата изменения |
| `capturedAt` | Дата съёмки, если адаптер может дать её дёшево (MediaStore, PhotoKit, EXIF); иначе пусто |
| `mimeType` | Если известен |
| `partialHash`, `fullHash` | Заполняются при поиске дублей |
| `lastSeenScanId` | В каком скане файл видели последний раз |

`fingerprint` — отпечаток файла из `size`, `modifiedAt`, `fullHash`. `withPartialHash` / `withFullHash` — копия с заполненным хешем (для кеша хешей в индексе).

### Fingerprint — отпечаток файла
`size` + `modifiedAt` + `fullHash` (если посчитан). Используется, чтобы перед операцией и перед откатом убедиться, что файл не изменился. Правило сравнения отпечатков (например, когда хеш есть только у одного) определяется в `executor` и `undo`.

### Category — категория
`documents`, `photos`, `videos`, `screenshots`, `music`, `archives`, `installers`, `other`, `unresolved`.

`unresolved` означает «правила не уверены». Такие файлы без ИИ остаются на месте и показываются в плане как «Не разобрано».

### Classification — результат классификации
`category`, опциональная `subfolder` (от ИИ, в этапе 1 не используется), `confidence` (0..1), `origin` (`rule` / `ai`), `reason` — `ClassificationReason`.

### Коды причин и ошибок (этап 2)
Ядро не формирует текстов для пользователя: причины и ошибки — sealed-классы с кодом и параметрами, тексты из них делает UI через локализацию. Равенство по значению.

- **`ClassificationReason`** (почему файл получил категорию): `ByUserRule(ruleId)`, `ByExtension(extension)`, `ScreenshotName`, `ScreenshotFolder`, `AiSuggestion`; для `unresolved` — `UnknownExtension(extension)`, `NoExtension`, `ScreenshotNameNotImage(extension)`, `MimeMismatch(mimeType, extension)`.
- **`OperationReason`** (почему в плане есть операция; `PlannedOperation.reason` и `Operation.reason`): `Classified(ClassificationReason)` — перемещение по классификации, `DuplicateOf(keeper)` — лишняя копия, `FolderFor(folder)` — папка для целевой папки плана, `MovePlaceholder(file)` — пустая заготовка, которую прерванное перемещение `file` оставило на месте цели (её помещает в карантин `recovery`, 4.9; планировщик такую причину не создаёт), `LegacyReason(text)` — текст из схемы БД версии 1 (ядро его не создаёт).
- **`OperationProblem`** (`Operation.error`: почему операция не выполнена, пропущена или не откачена):
  - выполнение: `FileGone`, `NotAFile`, `FileChanged`, `NotADuplicate` (копия не в группе или изменилась), `KeeperChanged(keeper)` (сохраняемый экземпляр изменился или исчез), `DependsOnMissingFolder(folder)`, `FolderExists`;
  - откат: `FolderNotEmpty`, `NotWhereCleanupPutIt`, `FileChanged`, `NotAFile`, `QuarantinePurged`, `CannotRestore` (источник не умеет восстанавливать или не записана ссылка карантина), `FolderReplacedByFile(folder)`, `NoFreeName(original)`;
  - восстановление: `InterruptedOperation` (операция не успела выполниться), `NeedsAttention(cause, errorKind?)` — «требует внимания»: `fileLost` (файла нет ни на старом, ни на новом месте, ни в карантине), `cannotCheck`, `cannotSearchQuarantine`;
  - любой этап: `FileSystemError(kind, path?, detail?)` — ошибка `FileSource`: вид `FileErrorKind`, путь, если ошибка не о файле самой операции (сохраняемая копия, папка на пути назначения), и техническая подробность адаптера (для журнала, не для показа);
  - `LegacyProblem(text)` — текст из схемы БД версии 1.
- **`FileErrorKind`** лежит в модели (`core/model/file_error_kind.dart`), чтобы UI мог показывать `FileSystemError`, не импортируя порты; `core/ports/file_error.dart` его реэкспортирует.

`subfolder` — это `LogicalPath` (не корень), поэтому подпапка от ИИ не может выйти за пределы папки категории. У `unresolved` подпапки нет.

### ClassificationRule — пользовательское правило классификации
`id`, `category`, `priority` (меньше — раньше; затем по `id`) и условия, которые должны выполняться все: `extensions` (без точки, в нижнем регистре), `nameContains` (подстрока имени без учёта регистра), `folder` (файл внутри папки на любой глубине; корень — где угодно), `sourceId` (пусто — все источники). Нужно хотя бы одно условие. Правило с `unresolved` оставляет подходящие файлы на месте.

### Zone — зона
`chaos` (убирать), `organized` (не трогать), `excluded` (не трогать и не сканировать), `target` (папки шаблона, куда складываются файлы).

### ZoneOverride — зона, заданная пользователем
`sourceId`, `folder` (корень — весь источник), `zone` — только `chaos`, `organized` или `excluded` (`target` задаёт только шаблон). Действует на папку и все её подпапки. Подробнее о приоритете — в 4.2.

### DuplicateGroup — группа дублей
`fullHash`, список файлов (хранится отсортированным по пути), выбранный `keeper` и причина выбора `keeperReason`.

`KeeperReason` соответствует правилам выбора из 4.3 (первое правило, которое различает файлы): `organizedLocation`, `earliestModified`, `notACopy`, `shortestPath`, `alphabeticalPath`.

Инварианты: не меньше двух файлов; все из одного источника; пути различны; одинаковый ненулевой размер; у каждого файла `fullHash` равен хешу группы; `keeper` входит в группу.

Производные значения: `extras` (лишние экземпляры), `size`, `reclaimableBytes`.

### OperationType — тип операции
`mkdir`, `move`, `quarantine`, `addToAlbum`. Какие поля использует операция, зависит от типа:

| Тип | `fromPath` | `toPath` | `fingerprint` |
|---|---|---|---|
| `mkdir` | — | создаваемая папка | — |
| `move` | файл | новое место (≠ `fromPath`, не внутри `fromPath`) | обязателен |
| `quarantine` | файл | — | обязателен |
| `addToAlbum` | файл | — | обязателен |

Пути операций не могут быть корнем источника. Проверка — `OperationType.checkShape`, её используют и `PlannedOperation`, и `Operation`.

### Plan — план уборки
- `PlannedOperation` создаётся фабриками `mkdir`, `move`, `quarantine`, `addToAlbum`. У каждой операции: тип, источник, путь «откуда», путь «куда», отпечаток файла, причина, ключ группы, флаг «одобрена» (задаётся явно). `withApproved` меняет только одобрение.
- `Plan.operations` — операции **в порядке выполнения**.
- `Plan.groups` — производное представление: `PlanGroup` по `groupKey` в порядке первой операции группы («Дубли», «В Документы», «В Фото / 2024» и т.д.).
- `Plan.unresolved` — неразобранные файлы. Операций для них нет, они показываются в плане как «Не разобрано».
- `Plan.duplicateGroups` — все найденные группы дублей, в том числе с копиями вне зон хаоса, которые не получают операций и только показываются («ещё N копий в ваших папках»).
- `Plan.isEmpty` — **нет операций**. Неразобранные файлы не делают план непустым (инвариант 7).
- Сводка `PlanSummary`: `fileCount` (операции над файлами, без `mkdir`) и `reclaimableBytes` (размер файлов в `quarantine` и `addToAlbum`). Есть сводка по всем операциям (`summary`) и только по одобренным (`approvedSummary`).

### QuarantineRef — ссылка на объект в карантине
Непрозрачная непустая строка, которую понимает только создавший её адаптер (своя папка-карантин, системная корзина или альбом).

### Settings — настройки
- `quarantineRetention` — срок хранения карантина: по умолчанию 30 дней, не меньше 1 дня (ошибка в настройке не должна очистить карантин сразу после уборки).
- `layoutFolderNames` — названия папок шаблона по категориям; фиксируются при первом запуске по языку системы, смена языка интерфейса их не меняет (иначе появился бы второй комплект папок). Пусто — ещё не зафиксированы. Проверяются по правилам шаблона (`checkLayoutFolderNames`, 4.5).
- `uiLocale` — язык интерфейса (тег BCP 47); пусто — язык системы.

`copyWith` меняет отдельные поля (язык можно сбросить к системному).

### ScanCursor и ScanCheckpoint — возобновление скана
`ScanCursor` — непрозрачная позиция в листинге источника; её выдаёт `FileSource` после каждой страницы, и с неё листинг продолжается.

`ScanCheckpoint` — где остановился незавершённый скан источника: `sourceId`, `scanId`, `stage` (`listing` — идёт листинг, `cursor` указывает на последнюю проиндексированную страницу; `finalizing` — листинг завершён, из индекса удаляются исчезнувшие файлы), `cursor`.

### Operation — запись журнала
| Поле | Описание |
|---|---|
| `id`, `sessionId`, `seq` | Порядок внутри сессии (`seq` ≥ 0) |
| `type` | `mkdir`, `move`, `quarantine`, `addToAlbum` |
| `sourceId`, `fromPath`, `toPath` | Что и куда (см. `OperationType`) |
| `fingerprint` | Отпечаток файла на момент планирования |
| `quarantineRef` | Ссылка на объект в карантине (только для выполненных `quarantine`) |
| `reason`, `groupKey` | Для отчёта и частичного отката |
| `status` | `pending`, `done`, `failed`, `skipped`, `reverted`, `revertSkipped` |
| `error` | Описание ошибки или причины пропуска. Есть ровно у `failed`, `skipped`, `revertSkipped` |
| `executedAt` | Когда операция вышла из `pending`. Есть ровно у не-`pending` |
| `revertedAt` | Когда операция откачена. Есть ровно у `reverted` |

Новая запись создаётся `Operation.pending` из `PlannedOperation`. Статус меняется только методами `markDone`, `markFailed`, `markSkipped`, `markReverted`, `markRevertSkipped` по разрешённым переходам:

```
pending → done | failed | skipped
done → reverted | revertSkipped
revertSkipped → reverted | revertSkipped   (повторная попытка отката)
failed, skipped, reverted — конечные
```

В `pending` вернуться нельзя.

### CleanupSession — сессия уборки
`id`, `startedAt`, `finishedAt`, `status`, `stats`.

Статусы и переходы (`transitionTo`):

```
planned → running | cancelled
running → completed | failed | cancelled
completed | failed | cancelled | partiallyReverted → reverted | partiallyReverted
reverted — конечный
```

`finishedAt` — время окончания выполнения: задаётся ровно при переходе в `completed`, `failed` или `cancelled` и сохраняется при откате. Не раньше `startedAt`.

`SessionStats` — сводная статистика: `total`, количество операций по статусам (`done`, `failed`, `skipped`, `reverted`, `revertSkipped`; `pending` вычисляется) и `removedBytes` — размер файлов, которые сейчас убраны (`quarantine` и `addToAlbum` в статусах `done` и `revertSkipped`). Считается из журнала: `SessionStats.of(operations)`.

## 3. Порты (`core/ports/`)

Публичный вход: `core/ports/ports.dart`.

### FileSource — работа с файлами одного источника

Один экземпляр работает с одним источником (`sourceId`).

| Метод | Вход | Выход |
|---|---|---|
| `capabilities` | — | `SourceCapabilities` |
| `appFolders` | — | Папки, которые адаптер держит внутри источника для себя (например, свой карантин). Исключаются из любой уборки и не сканируются |
| `list` | курсор `after` (для возобновления), `skipFolder` (в какие папки не заходить) | Поток `FileResult<FileListPage>`: файлы страницы (`FileEntry` без хешей и без `lastSeenScanId`), недоступные папки `inaccessible`, курсор после страницы. Порядок стабильный. Ошибка завершает поток |
| `stat` | путь | `FileStat` (`file` / `directory`, размер, дата изменения) или `notFound` |
| `exists` | путь | да / нет |
| `partialHash` | путь, необязательный `CancelToken` | Хеш размера и первых и последних 64 КБ |
| `fullHash` | путь, необязательный `CancelToken` | Полный хеш (адаптер считает потоково). Отменённый токен адаптер проверяет между блоками чтения и возвращает `cancelled` |
| `mkdir` | путь | Создаёт **одну** папку; родитель должен существовать (`notFound`). Так каждая созданная папка попадает в журнал. Если путь занят — `targetExists` |
| `move` | откуда, куда | Только файлы (`wrongType` для папки). Папка назначения должна существовать. **Никогда не перезаписывает:** если цель занята — `targetExists` |
| `quarantine` | путь, id сессии | `QuarantineRef` (своя папка-карантин или системная корзина). Только файлы |
| `findQuarantined` | id сессии, исходный путь | `QuarantineRef` объекта, который `quarantine` сделал для этого файла в этой сессии, или пусто (не помещался или уже очищен). Только чтение; нужен `recovery`, чтобы найти ссылку, не успевшую попасть в журнал |
| `restore` | `QuarantineRef`, путь назначения | Не перезаписывает (`targetExists`). Если объект карантина очищен — `notFound` |
| `removeEmptyDir` | путь | Удаляет только пустую папку (`notEmpty`, `wrongType` для файла) |
| `purgeQuarantined` | `QuarantineRef` | **Единственное удаление в системе** |
| `addToAlbum` | путь | Добавляет фото в альбом «На удаление» (iOS Photos). Фото остаётся на месте |
| `removeFromAlbum` | путь | Убирает фото из альбома «На удаление». **Само фото не удаляется** — это не удаление файла |

Правила для всех реализаций:
- Все методы возвращают `FileResult<T>` — sealed: `FileSuccess(value)` или `FileFailure(FileError)`. Ожидаемые ошибки не бросаются исключениями.
- Неудачный вызов ничего не меняет.
- Метод, который источник не умеет (см. `capabilities`), возвращает `unsupported`.
- Виды ошибок `FileErrorKind`: `notFound`, `targetExists`, `permissionDenied`, `locked`, `unsupported`, `notEmpty` (папка не пуста), `wrongType` (ожидался файл, а это папка, или наоборот), `cancelled` (вызов отменён `CancelToken`, ничего не изменилось), `ioError`.
- `CancelToken` (`core/ports/cancel_token.dart`) — позволяет остановить уже идущее чтение: вызывающий держит токен и вызывает `cancel()`, адаптер проверяет `isCancelled` или ждёт `whenCancelled` (`Future<void>`, завершается при `cancel()`, сразу — если токен уже отменён; нужен, когда чтение идёт в другом изоляте). Повторный `cancel()` ничего не делает. Токен одноразовый.

Поведение порта проверяет контрактный тест `test/contracts/file_source_contract.dart` через сам порт. Он состоит из двух частей: `fileSourceReadContract` (листинг, `stat` / `exists`, хеши, отмена) и `fileSourceWriteContract` (`mkdir`, `move`, карантин, `removeEmptyDir`, альбом); `fileSourceContract` — обе. `InMemoryFileSource` проходит обе части; POSIX-адаптер этапа 2 (`lib/platform/posix/`) — часть чтения на Linux (задача 6), запись — с задачи 7, затем Android.

### Classifier — классификация
| Метод | Вход | Выход |
|---|---|---|
| `classify` | пачка `ClassificationRequest` (`FileEntry` + зона его папки; родительская папка — `file.path.parent`) | `Classification` для каждого запроса в том же порядке |

Классификатор, который не может решить (в том числе при сбое облака), возвращает `unresolved`, а не ошибку.

Реализации: `RuleClassifier` (в ядре), облачный (позже, вне ядра), `FakeClassifier` для тестов.

## 4. Модули

### 4.1 `scan` — сканирование и индекс
**Ответственность:** обойти включённые источники и поддерживать индекс в актуальном состоянии.

`Scanner.scan(source, skipFolder)` сканирует один источник; включённые источники по очереди обходит `workflow`. Скан только читает источник и никогда не меняет файлы.

- Инкрементальность: файл с теми же `size` и `modifiedAt` не переиндексируется, его хеши сохраняются.
- Изменённый файл (другой размер или дата изменения): метаданные обновляются, хеши сбрасываются. Изменение содержимого при тех же размере и дате скан не замечает — это ловит проверка отпечатка с полным хешем перед операцией.
- Каждая запись получает `lastSeenScanId` текущего скана.
- Исчезнувшие файлы (не встреченные в текущем скане) удаляются из индекса — только после полного листинга. Неудачный или прерванный скан ничего не удаляет.
- Возобновляемость: после каждой страницы сохраняется курсор в `ScanCheckpointRepository` (`listing`). После листинга — этап `finalizing` (удаление исчезнувших), затем точка сбрасывается. Следующий вызов продолжает незавершённый скан с тем же `scanId`: с курсора или сразу с `finalizing`.
- Исключённые зоны не сканируются вовсе: в папки, для которых `skipFolder` возвращает `true`, скан не заходит, и их файлы уходят из индекса. Предикат передаёт `workflow` из модуля `zones` (`ZoneMap.skipFolder`). Исключение — папки проектов: они распознаются по содержимому после скана (см. 4.2).
- Недоступные папки попадают в сводку; их файлы не индексируются.
- Отдаёт поток событий: `ScanProgress` (источник, обработано файлов) после каждой страницы, в конце `ScanCompleted` со сводкой `ScanSummary` (добавлено, обновлено, без изменений, удалено, недоступные папки, был ли скан возобновлён) или `ScanFailed` с ошибкой листинга.
- Отмена — отписка от потока: скан останавливается после текущей страницы, курсор уже сохранён.

**Тесты:** первый скан, повторный без изменений (хеши не пересчитываются), изменение, удаление, исключённые папки, недоступные папки, прерывание (сбой, отмена, ошибка листинга) и возобновление, в том числе с этапа `finalizing`.

### 4.2 `zones` — зоны и исключения
**Ответственность:** для каждой папки и файла определить зону.

`ZoneMap` строится для одного источника из `ZoneConfig` (папки шаблона, собственные папки приложения), пометок пользователя `ZoneOverride` и файлов индекса. Для папки или файла возвращает `ZoneDecision`: зону, причину `ZoneReason` (для UI и тестов) и папку, чьё правило сработало. Все имена сравниваются без учёта регистра. Списки правил по умолчанию — `ZoneDefaults`.

**Приоритет** (от сильного к слабому):

1. **Исключения** — жёсткие: наследуются подпапками, пользователь не может их снять (может только добавить свои).
   - Скрытые папки (начинаются с `.`).
   - Папки разработки где угодно: `node_modules`, `build`, `target`, `__pycache__`, `venv`, `Pods`, `*.xcodeproj` и т.п.
   - Системные: где угодно — `AppData`, `$Recycle.Bin`, `System Volume Information`, `LOST.DIR`; от корня источника — `Android/data`, `Android/obb`, `Windows`, `Program Files`, `ProgramData`, `Library`, `Applications`.
   - Собственные папки приложения (карантин) из `ZoneConfig.appFolders`.
   - **Папки проектов:** папка, где лежит файл сборки (`pubspec.yaml`, `package.json`, `pom.xml`, `build.gradle`, `Cargo.toml`, `go.mod`, `Makefile`, `*.sln` и т.п.), исключается целиком — иначе файлы проекта разъехались бы по шаблону. Случайный файл сборки прямо в корне, `Download`/`Desktop` или в папке мессенджера эти папки не исключает.
   - Папки, исключённые пользователем.
2. **Целевые папки** шаблона (`ZoneConfig.targetFolders`, см. 4.5) и всё внутри — `target`.
3. **Ближайшая пометка пользователя** на папке или её родителе — `chaos` или `organized`. Пометка действует на все подпапки; более глубокая пометка сильнее.
4. **Зоны по умолчанию:**
   - хаос — **только файлы, лежащие непосредственно** в корне источника и в папках загрузок и рабочего стола в корне (`Download(s)`, `Desktop`, `Загрузки`, «Рабочий стол» и их варианты на других языках), а также в `Telegram Desktop` внутри такой папки. **Подпапки этих папок не трогаются** (например, `Download/project`, `Desktop/Новая папка`, чат-экспорты Telegram), пока пользователь не пометит их как хаос;
   - хаос с **всеми подпапками** — медиапапки мессенджеров: `Telegram`, `WhatsApp/Media`, их варианты в `Android/media/...`, `Viber/media`;
   - всё остальное — `organized` (например, `DCIM`, `Documents`).

**Исключения на уровне файлов** (только в безопасную сторону): скрытые файлы, системные (`desktop.ini`, `Thumbs.db`), незавершённые загрузки и временные файлы (`.crdownload`, `.part`, `.tmp` и т.п.), lock-файлы Office (`~$…`). Перенос такого файла сломал бы загрузку или открытый документ. Остальные файлы получают зону своей папки.

**Сканирование:** `skipFolder` — исключения, видимые по пути (всё, кроме папок проектов); его передают в `scan`, и такие папки не сканируются вовсе. Папки проектов определяются по содержимому, поэтому их файлы попадают в индекс, но получают зону `excluded` и ни в чём не участвуют.

Эвристика «организованности» (число файлов, преобладание категории, структура) в этапе 1 не используется: подпапки и так не трогаются. Её можно вернуть позже как подсказку «похоже на свалку — убрать?».

**Тесты:** каждое правило по отдельности; приоритет пользовательских настроек и его границы (исключения и шаблон сильнее); вложенность (исключённая папка внутри зоны хаоса, пометка внутри пометки); сценарии Download, телефон, архив документов.

### 4.3 `dedupe` — поиск дублей
**Ответственность:** найти группы идентичных файлов и выбрать, какой оставить.

`DuplicateFinder.find(source, zones)` работает с одним источником и только читает файлы.

- Каскад: группировка по размеру → частичный хеш → полный хеш. Файлы до 128 КБ (`fullHashOnlyUpTo`) сразу хешируются полностью: частичный хеш (начало и конец по 64 КБ) всё равно прочитал бы файл целиком.
- Хеши кешируются в индексе: имеющиеся берутся оттуда, посчитанные записываются обратно (`FileEntry.withPartialHash` / `withFullHash`). Скан сбрасывает их у изменённых файлов (4.1).
- Пустые файлы (0 байт) дублями не считаются.
- Дубли ищутся только внутри одного источника.
- Файлы в исключённых зонах (включая исключённые файлы, см. 4.2) не участвуют.
- Файл, который не удалось захешировать (заблокирован, исчез после скана, нет доступа), исключается из поиска и попадает в отчёт `skipped`; поиск продолжается.
- **Выбор экземпляра для сохранения** (`chooseKeeper`; по порядку, до первого различия):
  1. лежит в организованной или целевой папке, а не в зоне хаоса;
  2. более ранняя дата изменения;
  3. имя без признаков копии (`hasCopyMarker`: `(1)`, `(2)`, `copy`, `copy 2`, `- Copy`, `Copy of`, `копия`, `Kopie` и т.п.);
  4. более короткий путь;
  5. детерминированный выбор по алфавиту пути.

  Причина выбора (`KeeperReason`) — правило, которое отличило keeper от ближайшего конкурента. Результат не зависит от порядка файлов.
- Группа попадает в результат независимо от зон экземпляров. Операции получают только лишние экземпляры **из зон хаоса** (см. 4.6); копии в организованных и целевых папках только показываются.
- Отдаёт поток: `DedupeProgress` после каждой группы одинакового размера (сделано / всего, сколько хешей посчитано), в конце `DedupeCompleted` с группами (по пути keeper) и пропущенными файлами. Отмена — отписка от потока (после текущей группы размера) или `CancelToken` в `find(..., cancel:)` — хеширование останавливается внутри текущего файла, поток завершается без `DedupeCompleted`, отменённый файл не считается пропущенным. Посчитанные хеши остаются в индексе.

**Тесты:** каскад (разный размер, совпадение частичного хеша при разном полном, маленькие файлы, несколько групп одного размера), пустые файлы, зоны, кеш хешей, ошибки хеширования, каждое правило выбора и их порядок, детерминированность, прогресс и отмена (отпиской и токеном посреди файла).

### 4.4 `classify` — классификация правилами
**Ответственность:** определить категорию файла без ИИ.

`RuleClassifier` реализует порт `Classifier`; `classifyFile` — синхронно для одного файла. Порядок:

1. **Пользовательские правила** (`ClassificationRule`) в порядке из `RuleRepository`; первое подходящее побеждает. Они имеют приоритет над встроенными.
2. **Скриншоты:** изображение (`png`, `jpg`, `jpeg`, `webp`, `heic`, `heif`), имя которого начинается с `Screenshot`, `Screen Shot`, «Снимок экрана», «Скриншот», или которое лежит непосредственно в папке `Screenshots` / «Скриншоты».
3. **По расширению** (`BuiltinRules`, регистр не важен):
   - `documents`: pdf, doc(x), xls(x), ppt(x), odt, ods, odp, rtf, txt, csv, epub, md, djvu, fb2, pages, numbers, key;
   - `photos`: jpg, jpeg, heic, heif, png, webp, gif, bmp, tif(f), raw-форматы (cr2, cr3, nef, arw, dng, raf, orf, rw2);
   - `videos`: mp4, mov, mkv, avi, webm, m4v, 3gp, wmv, mts;
   - `music`: mp3, flac, m4a, wav, ogg, aac, opus, wma, alac;
   - `archives`: zip, rar, 7z, tar, gz, tgz, bz2, xz;
   - `installers`: apk, apks, xapk, exe, msi, dmg, pkg, deb, rpm, appimage;
   - `other` — известные типы, которые не подходят под остальные категории: torrent, ics, vcf, ttf, otf, gpx, kml.

**`unresolved`:** неизвестное расширение или его отсутствие; противоречивые признаки — имя скриншота у не-изображения (`Screenshot.pdf`) или MIME-тип другого медиасемейства, чем расширение (`image/png` у `.pdf`, `application/pdf` у `.jpg`). Общие MIME-типы (`application/octet-stream`) противоречием не считаются.

Результат правил: `origin = rule`, `confidence` 1 (0 для `unresolved`), `reason` — `ClassificationReason` (`ByExtension('pdf')`, `ByUserRule(id)`, `UnknownExtension('xyz')` и т.д., см. 2).

`ClassificationPipeline`: сначала правила, затем ИИ (если задан) только для `unresolved`, порядок результатов сохраняется. В этапе 1 ИИ не задан — работают только правила. Классификатор, вернувший не столько результатов, сколько запросов, — ошибка (`StateError`).

**Тесты:** таблица «файл → ожидаемая категория» (все расширения, скриншоты, противоречия), приоритет и условия пользовательских правил, конвейер с ИИ-заглушкой.

### 4.5 `layout` — шаблон структуры папок
**Ответственность:** превратить классификацию в целевой путь.

- Шаблон `LayoutTemplate`: `<документы>/`, `<фото>/<год>/`, `<видео>/<год>/`, `<скриншоты>/<год>/`, `<музыка>/`, `<архивы>/`, `<установщики>/`, `<прочее>/`.
- Названия папок берутся из локализации и передаются в ядро параметром; в ядре своих названий нет. Каждая категория, кроме `unresolved`, должна иметь название: одна папка, не начинается с точки, названия различаются без учёта регистра.
- Корень шаблона внутри источника — настраиваемый (по умолчанию корень источника). `targetFolders` — папки верхнего уровня шаблона, их получают зоны (4.2).
- Год: `capturedAt`, если есть, иначе `modifiedAt`. Функция года `yearOf` — параметр: даты в ядре хранятся в UTC, а приложение передаёт местный год (фото, снятое в 00:30 1 января по местному времени, попадает в новый год). По умолчанию — год в UTC.
- Подпапка от ИИ (`Classification.subfolder`) идёт внутрь папки категории после года.
- `place(file, classification)` → `PlaceIn(папка)` или `StaysInPlace`:
  - `unresolved` → целевого пути нет, файл остаётся на месте;
  - **файл уже в своей целевой папке** (сравнение без учёта регистра) → операции нет.
- **Конфликт имён** (`NameAllocator`): имя занято, если по этому пути что-то есть (`taken` — файлы и папки источника) или его уже заняла другая операция плана; тогда добавляется суффикс ` (2)`, ` (3)` и т.д. Имена **всегда сравниваются без учёта регистра** (на Windows и Android `A.jpg` и `a.jpg` — один файл; на остальных системах это даёт только лишний суффикс). Составные расширения не разрываются: `archive (2).tar.gz`. Это планирование «по возможности»: перезапись всё равно невозможна, `move` порта возвращает `targetExists`.

**Тесты:** пути для каждой категории, год из `capturedAt` и `modifiedAt` и по местному времени, корень шаблона, подпапка, конфликты имён (на диске, внутри одного плана, разный регистр, без расширения, составные расширения), отсутствие операции для уже разложенного файла, проверка названий папок.

### 4.6 `planner` — построение плана
**Ответственность:** собрать план из результатов дедупликации, классификации и шаблона.

`Planner.plan(source, files, zones, duplicates)` → `PlanOutcome`: `PlanReady(plan)` или `PlanInvalid(plan, violations)`. Планирование только читает источник.

- **Дубли:** лишние экземпляры **из зон хаоса** → `quarantine`; если у источника нет карантина, но есть альбом (iOS Photos) — `addToAlbum`; если нет ни того, ни другого — операции нет. Лишние экземпляры не классифицируются и не перемещаются.
- **Дубли вне зон хаоса (решение):** лишние экземпляры в организованных и целевых папках операций не получают никогда — ни одобренных, ни неодобренных; группа показывается в плане как информация (`Plan.duplicateGroups`). Чтобы убрать дубли внутри своей папки, пользователь помечает её как хаос (4.2). Режим «почистить дубли в моих папках» с отдельным подтверждением — возможное расширение после этапа 1.
- Сохраняемый экземпляр (если он в хаосе) и остальные файлы из зон хаоса → классификация → `move` в целевой путь (`LayoutTemplate.place`, имя — `NameAllocator`, занятыми считаются все пути индекса). `unresolved` → `Plan.unresolved`. Без `canMove` перемещений нет.
- **Папки:** `mkdir` только для отсутствующих папок — проверяется через `FileSource.exists`, а не по индексу (в индексе нет пустых папок). Родитель создаётся раньше ребёнка, папка — прямо перед первым перемещением в неё. Папку, состояние которой не удалось проверить (например, нет доступа), план не использует. Без `canMkdir` — перемещения только в существующие папки.
- **Порядок** (детерминированный): сначала операции с дублями (по пути keeper), затем по целевым папкам в порядке пути: их `mkdir`, затем перемещения в порядке исходного пути. Результат не зависит от порядка входных данных.
- **Группы:** `duplicates` и `move:<папка>` (например, `move:Фото/2024`); `mkdir` относится к группе папки, ради которой создан. Все операции одобрены. Причина: для дубля — `DuplicateOf(keeper)`, для перемещения — `Classified(<причина классификации>)`, для папки — `FolderFor(<папка>)`.
- **Валидация плана** (`PlanValidator`; нарушение — `PlanInvalid`, а не молчаливый пропуск):
  - ни одна операция не перезаписывает файл: цель свободна и не занята дважды (сравнение без учёта регистра);
  - ни одна операция не выходит за пределы источника;
  - файлы берутся только из зон хаоса и кладутся только в целевые папки; папки создаются только в целевых папках или на пути к ним (например, собственный корень шаблона) — исключённые, организованные и уже разложенные файлы не затрагиваются;
  - тип операции поддерживается источником;
  - один файл (точный путь) участвует не больше чем в одной операции;
  - у каждой создаваемой папки и цели перемещения есть родитель: существующий или созданный раньше в плане.
- **Идемпотентность:** повторное планирование после выполнения плана даёт пустой план (неразобранные файлы и копии вне хаоса остаются, но операций для них нет).

**Тесты:** сценарии «папка Download с типичным мусором» (полный план), телефон, архив документов; дубли вне хаоса (все в организованных, смешанные, в целевых папках) и дубль + перемещение keeper; конфликты имён (на диске, в одном плане, разный регистр); существующие и недоступные папки, собственный корень шаблона; возможности источника (iOS, без карантина, без mkdir); пользовательские зоны; каждое правило валидатора. Инварианты 1, 5, 6, 7, 8 — на сценариях и на 60 случайных деревьях (`randomTree`, в том числе без учёта регистра).

### 4.7 `executor` — выполнение
**Ответственность:** выполнить одобренные операции плана безопасно и с журналом.

`Executor.start(source, plan)` → `ExecutionRun`: `sessionId`, поток `progress` (после каждой операции: всего, выполнено, пропущено, ошибок, последняя операция), `result` (итоговая сессия), `cancel()`. План другого источника отвергается сразу (`ArgumentError`).

- Сессия создаётся в `planned` и сразу переходит в `running`; в конце — `completed` (ошибки и пропуски отдельных операций входят в статистику) или `cancelled`. Статистика — `SessionStats.of(журнал сессии)`.
- Неодобренные операции не попадают в журнал и не выполняются.
- Для каждой одобренной операции, в порядке плана:
  1. записать в журнал со статусом `pending` (инвариант 3);
  2. если операция зависит от папки, которую не удалось создать (цель внутри неё), — `skipped`;
  3. проверить файл:
     - для `move` / `quarantine` / `addToAlbum` — размер и дата изменения через `stat` совпадают с отпечатком плана; файл исчез, стал папкой или изменился — `skipped`. Хеш перед `move` **не** пересчитывается (это перечитывание всех файлов уборки); перемещение изменившегося файла безопасно — файл остаётся у пользователя, откат его вернёт;
     - **для `quarantine` / `addToAlbum` дубля** полный хеш лишнего экземпляра **и** keeper пересчитывается заново, а не берётся из кеша: кеш мог устареть, если содержимое изменилось при тех же размере и дате. Keeper ищется там, куда его переместила эта же сессия. Хеши не совпадают с `DuplicateGroup.fullHash`, keeper исчез или не читается — `skipped`. Операция карантина вне групп `plan.duplicateGroups` — `skipped`: в карантин уходят только проверенные дубли;
  4. выполнить через `FileSource`;
  5. записать `done` (с `quarantineRef` для `quarantine`) или `failed` с ошибкой `FileSystemError`.

  Коды пропуска (`skipped`): `DependsOnMissingFolder`, `FileGone`, `NotAFile`, `FileChanged`, `NotADuplicate`, `KeeperChanged`, `FolderExists`, `FileSystemError` (не удалось проверить или захешировать; для сохраняемой копии — с её путём).
- `mkdir` папки, которая уже существует (появилась после планирования), — `skipped` (`FolderExists`): зависимые перемещения продолжаются, а откат такую папку не удаляет. Любая другая ошибка `mkdir` — `failed`, и всё, что внутри этой папки, получает `skipped`.
- Ошибка одной операции не останавливает уборку.
- **Отмена:** `cancel()` — после текущей операции уборка останавливается, сессия получает статус `cancelled`; оставшиеся операции не попадают в журнал. Уже выполненное можно откатить. Выполнение не зависит от подписчиков: отписка от `progress` уборку не останавливает (в отличие от скана и поиска дублей, которые только читают). Прогресс доставляется синхронно, так что отмена из обработчика срабатывает до следующей операции.
- **Падение процесса** (`SimulatedCrash` в тестах) ничем не перехватывается: текущая операция остаётся `pending`, сессия — `running`; это разбирает `recovery` (4.9).

**Тесты:** успешное выполнение (результат совпадает с планом, журнал, статистика, прогресс, повторный план пуст), изменённый / исчезнувший файл (`skipped`), ошибки ФС и занятая цель (`failed`, без перезаписи), зависимые операции и уже существующая папка, повторная проверка дублей (изменённая копия, изменённый или исчезнувший keeper, keeper перемещён в этой сессии, карантин вне группы), альбом iOS, отмена посередине и до начала, отписка без отмены, неодобренные операции, падение до и после вызова ФС, инвариант 3 (запись в журнал до вызова ФС и результат после).

### 4.8 `undo` — откат
**Ответственность:** вернуть файлы в исходное состояние.

`UndoService.start(source, sessionId, scope)` → `UndoRun` (источник можно не передавать, если откатывать нечего — сессия без операций): поток `progress` (`UndoEntry` после каждой операции), `result` (`UndoResult`: сессия и записи), `cancel()`. Как и `executor`, работает независимо от подписчиков; отмена — после текущей операции, сессия становится `partiallyReverted`.

- Режимы (`UndoScope`): вся сессия (`WholeSession`), по группе (`OneGroup(groupKey)`), отдельная операция (`OneOperation(id)`).
- Откатываются операции со статусом `done`, а также `revertSkipped` (повторная попытка после того, как пользователь устранил конфликт), в **обратном порядке** `seq`. `failed` и `skipped` ничего не меняли и не трогаются.
- Обратные операции:
  - `move` → перемещение обратно;
  - `quarantine` → `restore` по `quarantineRef`;
  - `mkdir` → `removeEmptyDir` (только если папка пуста);
  - `addToAlbum` → `removeFromAlbum`.
- **Проверки перед каждым возвратом:**

| Ситуация | Поведение |
|---|---|
| Файла нет на ожидаемом месте | `revertSkipped` (`NotWhereCleanupPutIt`) |
| Отпечаток изменился (размер или дата) | `revertSkipped` (`FileChanged`; решение пользователя — в UI, позже) |
| Исходное место занято другим файлом | Восстановить рядом: `имя (<метка>).ext`, затем `имя (<метка> 2).ext` и т.д. Метка («восстановлено») передаётся из локализации параметром `restoredLabel`; путь — в `UndoEntry.restoredAs` |
| Исходной папки нет | Создать (вместе с недостающими родителями; эти папки не журналируются) |
| Объект карантина уже очищен | `revertSkipped` (`QuarantinePurged`) |
| Источник не умеет восстанавливать из карантина | `revertSkipped` (`CannotRestore`) |
| Созданная уборкой папка не пуста (пользователь что-то положил, или в ней остались файлы другой группы при частичном откате) | `revertSkipped` (`FolderNotEmpty`); полный откат позже повторит |
| Папки уже нет / фото уже не в альбоме | `reverted` — цель уже достигнута |
| `quarantine` с причиной `MovePlaceholder` (пустая заготовка, 4.9) | `reverted` без восстановления: заготовки не было в исходном дереве. Она остаётся в карантине (откат ничего не удаляет); очистка по сроку её не берёт, так как операция откачена |

- Никогда ничего не перезаписывает: все действия идут через порт, занятая цель — `targetExists`.
- Папку, которую уборка создала, а пользователь потом пересоздал (например, вернув в неё файл), откат не удаляет повторно, если её `mkdir` уже был откачен.
- Итоговый статус сессии: `reverted`, если в журнале не осталось операций `done` / `revertSkipped`, иначе `partiallyReverted`. Повторный откат уже откаченной сессии ничего не делает.
- Нельзя откатить сессию, которая не завершила выполнение (`planned`, или `running` до `recovery`), — `StateError`.

**Тесты:** полный откат (дерево совпадает с исходным, порядок, статусы, статистика, повтор ничего не делает), частичный (группа, операция, общая папка, группы по одной), каждая конфликтная ситуация, повтор после `revertSkipped`, источник без восстановимого карантина, альбом iOS, откат отменённой сессии и сессии с ошибками, отказ для незавершённой сессии, отмена посреди отката. **Инвариант 4** — property-based тест `test/scenarios/undo_property_test.dart`: 120 случайных деревьев (в том числе без учёта регистра) → план → выполнение (в том числе со сбоями ФС и отменой посередине) → откат (в том числе сначала по группам в случайном порядке) → снимок совпадает с исходным.

### 4.9 `recovery` — восстановление после сбоя
**Ответственность:** при запуске приложения найти сессии в статусе `running` и привести журнал в соответствие с реальностью.

`Recovery` (журнал, сессии, `Clock`, `IdGenerator`): `interruptedSessions()` — сессии в `running`; `sourceOf(sessionId)` — источник сессии по журналу; `recover(sessionId, source:)`.

- После падения у сессии есть операции в статусе `pending`: записанные в журнал, но без результата (обычно одна). Для каждой проверяется файловая система:

| Операция | Проверка → статус |
|---|---|
| `move` A→B | файл ещё в A → `skipped`; иначе в B с размером и датой из отпечатка → `done`; иначе → `failed` |
| `mkdir` F | F — папка → `done`; иначе → `skipped` |
| `quarantine` A | файл ещё в A → `skipped`; иначе объект найден в карантине (`findQuarantined`) → `done` с его `quarantineRef`; иначе → `failed` |
| `addToAlbum` A | фото на месте → `done` (была ли операция выполнена, не узнать, но отмена безопасна в обоих случаях); фото нет → `failed` |

  - Для `move` сначала проверяется **исходное** место: перемещение атомарно, файл в A значит, что оно не выполнялось, что бы ни лежало в B (там может быть посторонний файл того же размера и даты).
  - **Заготовка прерванного перемещения** (этап 2, решение A.5): адаптер без переименования «без перезаписи» сначала занимает имя цели пустым файлом, затем переименовывает поверх него. Падение между шагами оставляет файл в A и пустой файл в B. Поэтому для `move`, получившего `skipped`, если в B — пустой файл, изменённый не раньше начала сессии (с допуском `placeholderTolerance` = 2 с на грубое время ФС), и источник умеет карантин: в журнал добавляется новая операция `quarantine` B (следующий `seq`, та же группа, отпечаток размера 0, причина `MovePlaceholder(A)`) — сначала `pending`, затем выполняется (`done` с `quarantineRef` или `failed` с `FileSystemError`). Если `recovery` сам упал, следующий запуск доделывает её: `pending`-операция с причиной `MovePlaceholder`, чей пустой файл ещё на месте, выполняется, а не пропускается; вторая такая операция для того же файла не создаётся. Файл с содержимым или более старый не трогается.
  - `skipped` получает `InterruptedOperation`, `failed` — `NeedsAttention` («требует внимания»): `fileLost`, если файла нет ни на старом, ни на новом месте (ни в карантине); `cannotCheck` / `cannotSearchQuarantine` с видом ошибки, если файл или карантин не удалось проверить (например, нет доступа).
- После этого сессия закрывается статусом `failed` («выполнение не завершилось», с `finishedAt` и статистикой) и может быть откачена (4.8).
- **«Доделать» (решение):** новый план с текущего состояния в новой сессии — по инварианту 7 в нём ровно оставшаяся работа. Операции пишутся в журнал по одной перед выполнением (4.7), поэтому не начатые операции прерванного плана не хранятся, и продолжать «тот же» план не нужно. Запускает `workflow`.
- Отказы (`StateError` / `ArgumentError`): сессия неизвестна или не в `running`; есть `pending`, а источник не передан; источник не тот.

**Тесты:** падение до вызова ФС и после вызова ФС (но до записи `done`) для `mkdir`, `move`, `quarantine`, `addToAlbum`; после восстановления откат возвращает исходное дерево, а новый план доделывает уборку; «требует внимания» (файл нигде не найден, объект карантина исчез, нет доступа); `move` судится по исходному месту; заготовка прерванного перемещения (помещается в карантин новой журналируемой операцией, сначала `pending`; падение `recovery` до и после её выполнения — следующий запуск доделывает без второй операции; откат её не возвращает; старый или непустой файл и источник без карантина — не трогаются); сессия без `pending`; отказы. Property-based тест `test/scenarios/recovery_property_test.dart`: случайное дерево, падение на случайном изменяющем вызове в случайной точке → recovery → откат даёт исходное дерево, а повторное планирование и выполнение — пустой план.

### 4.10 `quarantine` — срок хранения карантина
**Ответственность:** очищать карантин по истечении срока (по умолчанию 30 дней, `Settings.quarantineRetention`).

`QuarantinePurger.purgeExpired(sources)` → `PurgeResult` (очищенные и оставленные с причиной).

- Для выполненных (`done`) операций `quarantine` старше срока (`doneQuarantinesBefore`) вызывается `purgeQuarantined`. Если объекта уже нет — считается очищенным.
- Очищенная операция получает `revertSkipped` с `QuarantinePurged` — то же состояние, которое даёт откат, когда находит карантин очищенным. По нему UI знает, что откат для этого файла невозможен; `quarantineRef` сохраняется для истории. Статистика сессии обновляется, статус — нет.
- Пропускаются (файл остаётся в карантине, причина — в результате):
  - источники, где карантин очищает сама ОС (`systemPurgesQuarantine`, системная корзина Android);
  - источники, которые сейчас недоступны;
  - сессии, ещё не прошедшие `recovery` (`running`);
  - операции, откат которых уже пытались выполнить (`revertSkipped`): пользователь хотел вернуть эти файлы;
  - операции, очистка которых не удалась (остаются `done`, попробуем в следующий раз).
- После очистки откат этих операций невозможен (4.8: `revertSkipped`, сессия — `partiallyReverted`).

**Тесты:** очистка по сроку (по умолчанию и из настроек), моложе срока — остаётся, повторная очистка ничего не делает, объект уже исчез, ошибка очистки; пропуск системных корзин, недоступных источников, невосстановленных сессий и файлов, откат которых пытались выполнить; откат после очистки.

### 4.11 `workflow` — сценарий уборки
**Ответственность:** единая точка входа для UI, конечный автомат уборки.

`CleanupWorkflow` получает репозитории (`WorkflowRepositories`), функцию «`FileSource` для источника» (`null`, если источник сейчас не открыть), `LayoutTemplate`, `Clock`, `IdGenerator`, метку «восстановлено» и, позже, облачный классификатор.

Состояния (`WorkflowState`):
```
idle → scanning → analyzing → planReady → executing → completed
  │       │           │           │            └→ cancelled
  │       └───────────┴→ idle     └→ idle (пользователь отказался)
  │       (отмена)
  ├→ failed (не удалось построить план)
  └→ interrupted (при запуске найдена прерванная сессия) → scanning («Доделать») | undoing («Откатить») | idle
completed / cancelled / interrupted / partiallyReverted → undoing → reverted / partiallyReverted
```

Команды (неподходящая для состояния команда или вторая команда, пока идёт первая, — `StateError`):
- `initialize()` — один раз при запуске: `recovery` прерванных сессий (4.9), затем очистка просроченного карантина (4.10). Если что-то восстановлено — `interrupted` (со списком; сессии, чей источник сейчас недоступен, остаются `running` и тоже перечислены), иначе `idle`. `start` вызывает `initialize` сам, если его не вызвали.
- `start()` — из `idle`, `interrupted` («Доделать» = новый план с текущего состояния), `failed` и конечных состояний. Для каждого включённого источника по очереди: скан с исключением зон и папок адаптера → зоны → дубли → классификация (пользовательские правила, затем ИИ, если задан) → план. Недоступный источник пропускается и попадает в `PlanReady.unavailable`. Ошибка листинга или план с нарушением правил безопасности → `failed` с причиной.
- `setGroupApproval` / `setOperationApproval` — только в `planReady`. Папки (`mkdir`) вручную не переключаются: папка одобрена тогда и только тогда, когда в неё идёт хотя бы одно одобренное перемещение.
- `execute()` — по одной сессии на каждый источник с одобренными операциями (4.7) → `completed` или `cancelled` (оставшиеся источники не трогаются).
- `undo()` — откат сессий последнего запуска (или восстановленных) в обратном порядке; все сессии запуска остаются в списке, так что повторный `undo` доделывает начатое. `undoSession(id, scope)` — любая завершённая сессия из истории, в том числе по группе или одной операции. Итог — `reverted` или `partiallyReverted`.
- `cancel()` — в `scanning` / `analyzing` → `idle` (скан продолжится с сохранённого места; хеширование останавливается внутри текущего файла через `CancelToken`, посчитанные хеши остаются); в `executing` / `undoing` — остановка после текущей операции. Когда ничего не идёт — ничего не делает.
- `dismiss()` — отказ от плана или подтверждение результата → `idle`.

- `state` — текущее состояние; `states` — поток: каждый подписчик сначала получает текущее состояние, затем изменения. Доставка асинхронная, в порядке изменений (UI подписывается через Riverpod).
- Одновременно может идти только одна уборка (одна команда).
- Ожидаемые сбои хранилища (`Exception`) переводят в `failed`; ошибки программы (`Error`, в том числе `SimulatedCrash` в тестах) не перехватываются.

**Тесты:** полный путь «кнопка → план → выполнение → откат» на двух источниках (последовательность состояний, прогресс, исходные деревья после отката, повторный план пуст); после падения — `interrupted`, «Доделать», «Откатить», откат из истории, недоступный источник; очистка карантина при запуске; одобрение (группа, общая папка, отдельная операция, запрет переключать папки); отмена при скане (скан возобновляется), выполнении (в том числе до первой операции), откате; недоступный и выключенный источники, папки адаптера, ошибка скана; пользовательские зоны и правила; откат с конфликтами; недопустимые команды; поток состояний.

## 5. Поток данных одной уборки

```
workflow.initialize()
  → recovery   : прерванные сессии → журнал приведён в порядок
  → quarantine : просроченный карантин → очищен
workflow.start()
  → scan       : источники → индекс
  → zones      : папки → зоны
  → dedupe     : индекс → группы дублей + keeper
  → classify   : файлы зон хаоса → категории
  → layout     : категории → целевые пути
  → planner    : всё вместе → Plan (валидированный)
  ⇢ UI: пользователь смотрит и одобряет
  → executor   : Plan → журнал + изменения ФС
  ⇢ UI: «Готово» / «Отменить»
  → undo       : журнал → обратные операции
```

## 6. Инварианты (проверяются тестами)

1. Ни один файл никогда не перезаписывается.
2. Удаление возможно только через `purgeQuarantined` и только для объектов карантина.
3. Каждая выполненная операция записана в журнал **до** выполнения.
4. Выполнение плана с последующим полным откатом возвращает файловую систему в исходное состояние (если между ними её никто не менял).
5. Операции не выходят за пределы источника.
6. Исключённые и организованные зоны не изменяются. Файлы, уже лежащие в целевых папках, тоже не перемещаются и не уходят в карантин — в том числе лишние копии дублей.
7. Повторная уборка сразу после завершённой даёт пустой план.
8. Результат планирования детерминирован: одинаковый вход → одинаковый план.

Инвариант 4 проверяется property-based тестом: случайное дерево файлов → план → выполнение → откат → сравнение с исходным деревом.

## 7. Тестовая инфраструктура (`app/test/support/`)

- **`InMemoryFileSource`** (`fs/`) — файловая система в памяти:
  - дерево файлов с содержимым (хеши считаются из содержимого);
  - настраиваемые возможности: пресеты `desktopCapabilities`, `androidMediaStoreCapabilities`, `iosPhotosCapabilities`;
  - режим без учёта регистра (`caseSensitive: false`) — как на Windows и Android;
  - хеширование блоками по `hashBlockSize` (64 КБ) с проверкой `CancelToken` перед каждым блоком; хук `onHashBlock` вызывается после каждого блока — так тест отменяет хеширование посреди файла;
  - **внедрение сбоев:** `failOn` — ошибка на N-м вызове, подходящем под фильтр (методы, путь), без эффекта; `crashOn` — `SimulatedCrash` (наследник `Error`, продакшен-код не должен его ловить) до или после эффекта, в том числе на N-й странице листинга; `lock` — заблокированный файл; `denyAccess` — отказ в доступе к папке и всему внутри;
  - **снимок состояния** `snapshot()` (файлы, папки, карантин, альбом) с `diff` для сравнения «до» и «после»; `tree` — только видимое дерево;
  - журнал вызовов порта `calls` / `mutations`;
  - «внешние» изменения в обход порта: `addFile`, `addDir`, `writeFile`, `removeExternally` (пользователь или другое приложение).
- **In-memory репозитории** (`repositories/`) для всех портов-репозиториев. `InMemoryOperationJournal.writes` хранит все записи по порядку.
- **`FakeClock`** (ручной и с автоматическим сдвигом) и **`SequentialIdGenerator`** (`id-1`, `id-2`, ...).
- **`FakeClassifier`** — ответы по пути, остальное `unresolved`; запоминает запросы.
- **Построители сценариев** (`scenarios.dart`, комбинируются в одном источнике): `withTypicalDownloadFolder` (типичная папка Download: документы, медиа, установщики, дубль с `(1)`, большой файл и «приманка» с тем же частичным, но другим полным хешем, нераспознаваемые файлы, пустой файл, `.cache` и `node_modules`), `withPhoneDuplicatePhotos` / `phoneStorage()` (телефон с дублями фото из WhatsApp, Telegram и Download), `withOrganizedDocumentArchive` (организованный архив документов).
- **Фикстуры модели** (`model_fixtures.dart`) и проверка равенства по значению (`value_equality.dart`).
- **`PipelineHarness`** (`pipeline_harness.dart`) — прогон «скан → зоны → дубли → план → выполнение → откат» как в `workflow`, плюс `recovery` и очистка карантина, с in-memory журналом, сессиями, настройками и `FakeClock`; `applyPlan` применяет план напрямую через порт (замена `executor` в тестах планировщика); `describe(plan)` — план построчно.
- **`randomTree(seed)`** (`random_tree.dart`) — воспроизводимое случайное дерево: зоны всех видов, признаки копий, варианты регистра, неизвестные расширения, дубли, папки проектов. Для property-based тестов.
- **`russianTemplate`** (`layout_fixtures.dart`) — шаблон с русскими названиями папок, как их передала бы локализация.
- **Контрактные тесты** (`test/contracts/`): один набор для каждого порта, который прогоняется против всех реализаций: `in_memory_contracts_test.dart` (in-memory репозитории и `InMemoryFileSource`), `drift_contracts_test.dart` (drift-репозитории на SQLite в памяти); POSIX-адаптер `FileSource` — в этапе 2.
- **`reason_fixtures.dart`** — по одному значению каждого кода причин и ошибок (и каждого параметра): тесты модели, кодека хранения и контракта журнала.
- **Архитектурный тест:** правила зависимостей всех слоёв `lib/` (белые списки, `docs/stage2_android.md`, раздел 11) и правила исходного кода `lib/platform/` (нет `rename`, удаление только в `purgeQuarantined` / `removeEmptyDir`).

## 7a. Слой данных (`lib/data/`, drift)

- **База** `AppDatabase` (`lib/data/db/`): таблицы в `tables.dart`, код drift генерируется в `app_database.g.dart` (`dart run build_runner build --delete-conflicting-outputs`). Генератор ограничен `lib/data/` в `build.yaml`. Исполнитель (файл на устройстве или память в тестах) передаётся снаружи; открытие файла БД на устройстве — при подключении приложения (этап 2).
- **Хранение:**
  - даты — `INTEGER`, микросекунды от эпохи в UTC (стандартные секунды drift потеряли бы микросекунды, и отпечатки перестали бы совпадать);
  - перечисления — `TEXT` с именем значения Dart: добавление значения не сдвигает старые, **переименование значения — изменение схемы**;
  - пути — `TEXT` с сортировкой `BINARY`: ключи с учётом регистра. Списки сортируются в Dart (`LogicalPath.compareTo`), потому что порядок байтов UTF-8 в SQLite расходится с порядком UTF-16 в Dart для некоторых символов (например, эмодзи);
  - настройки — таблица «ключ — значение»; отсутствующий ключ — значение по умолчанию (названия папок шаблона — JSON «категория → название», пустые настройки удаляют ключ);
  - причины и ошибки операций — `TEXT` с JSON `{"code": …, …параметры}` (`reason_codec.dart`); как и у перечислений, **переименование кода — изменение схемы**. Текст, который не является известным кодом (свободный текст версии 1, код более новой версии приложения), читается как `LegacyReason` / `LegacyProblem` с исходным текстом, а не ошибкой.
- **Репозитории** (`lib/data/repositories/`, `Drift…Repository`, `DriftOperationJournal`): журнал и сессии проверяют `RepositoryRules` внутри транзакции; пакетная запись индекса — одной транзакцией; `byPaths` разбивает список путей на пачки (лимит параметров SQLite).
- **Миграции:** `schemaVersion` = 2; при изменении схемы — увеличить версию, выполнить `dart run drift_dev make-migrations` (снимок схемы в `drift_schemas/`, помощник `app_database.steps.dart`, тесты в `test/data/migrations/`) и добавить шаг в `stepByStep`.
  - **v1 → v2 (этап 2):** колонка `sources.location` (у старых источников пустая); причины и ошибки операций переводятся в JSON `{"code":"legacy","text":<старый текст>}` (SQL `json_object`). Тест миграции проверяет схему и сохранность данных, а также что репозитории читают перенесённые строки как `LegacyReason` / `LegacyProblem`.
- **Тесты:** контрактные (см. 7), а также `test/data/`: кодек причин и ошибок (каждый код туда и обратно, стабильный формат, `legacy` для неизвестного текста), миграции, таблицы схемы, сохранность данных после переоткрытия файла БД, микросекунды и UTC, хранение перечислений по имени, порядок путей с эмодзи, `byPaths` больше одной пачки, отказ в записи журнала ничего не оставляет, сквозной сценарий `workflow` на SQLite (полный путь и падение с перезапуском на той же базе).
