## 2. Выполненные задачи

### Задача 1. Каркас
- Flutter SDK 3.47.6 (Dart 3.13.5) установлен в `~/development/flutter`.
- Flutter-проект в `app/`, org `com.brobrocode`, платформы android, ios, linux, macos, windows; пустой каркас приложения.
- Строгий анализатор: `strict-casts`, `strict-inference`, `strict-raw-types` и около 30 дополнительных правил.
- Структура папок по разделу 8.
- **Архитектурный тест** (`test/architecture/`): белые списки разрешённых библиотек Dart SDK и пакетов для `lib/core/`, запрет импортов остального приложения, `part`-директив и сгенерированных файлов. Ловит многострочные, условные, raw- и triple-quoted импорты, склейку строк, обход через `..`; если директиву не удалось разобрать — тест падает, а не молчит.

### Задача 2. Доменная модель
- Неизменяемые модели с равенством по значению (`@immutable`, единственная новая зависимость — `meta`).
- `LogicalPath` — путь внутри источника; пути с `..`, `.`, пустыми сегментами, ведущим `/` не создаются, поэтому операция структурно не может выйти за пределы источника.
- Идентификаторы — extension types (`SourceId`, `ScanId`, `SessionId`, `OperationId`).
- Даты нормализуются в UTC.
- Операции создаются фабриками, «форма» каждого типа проверяется (`move` требует откуда, куда и отпечаток и т.д.).
- Статусы операций и сессий меняются только по таблицам разрешённых переходов.

### Задача 3. Порты и тестовая инфраструктура
- Порты: `FileSource`, `Classifier`, `Clock`, `IdGenerator`, репозитории. Результаты `FileSource` — типизированные (`FileResult`), к видам ошибок добавлены `notEmpty` и `wrongType`.
- `InMemoryFileSource` — фейковая ФС с внедрением сбоев (ошибка на N-м вызове, `SimulatedCrash` до или после эффекта, блокировка, отказ в доступе), снимками состояния с diff, журналом вызовов, режимом без учёта регистра и пресетами возможностей (desktop, Android, iOS Photos).
- In-memory репозитории, `FakeClock`, `SequentialIdGenerator`, `FakeClassifier`, построители сценариев («типичная папка Download», «телефон с дублями фото», «организованный архив документов»).
- Контрактные тесты: `FileSource` проверяется только через сам порт — их можно будет прогнать против desktop-адаптера на реальной ФС.
- Правила защиты журнала и сессий (`RepositoryRules`) лежат в ядре и общие для всех реализаций.

### Задача 4. `scan`
- Инкрементальный скан: при тех же размере и дате хеши сохраняются, при изменении — сбрасываются.
- Исчезнувшие файлы удаляются из индекса только после полного листинга.
- Возобновление после сбоя, отмены или ошибки листинга с того же места и с тем же `scanId`.
- Исключённые папки не сканируются (`skipFolder`). В порт добавлен `byPaths` — пакетный поиск по путям страницы.

### Задача 5. `zones`
- Приоритет: жёсткие исключения → папки шаблона → ближайшая пометка пользователя → зоны по умолчанию.
- Хаос — только файлы прямо в корне и в папках загрузок и рабочего стола; их подпапки не трогаются. Медиапапки мессенджеров — хаос целиком.
- Исключаются папки проектов (по файлам сборки), а также отдельные файлы: скрытые, системные, незавершённые загрузки, lock-файлы Office.
- Модель `ZoneOverride` и порт `RuleRepository` (пометки зон).

### Задача 6. `dedupe`
- Каскад «размер → частичный хеш → полный хеш» внутри одного источника; хеши кешируются в индексе.
- Файлы до 128 КБ сразу хешируются полностью (частичный хеш всё равно прочитал бы их целиком).
- Выбор оставляемого экземпляра — пять правил по порядку; причина — правило, отличившее его от ближайшего конкурента.
- Распознавание признаков копии в имени (`(1)`, `- Copy`, `copy 2`, `копия` и др.).

### Задача 7. `classify` + `layout`
- Классификация правилами: пользовательские правила → скриншоты → расширение; противоречивые признаки (имя скриншота у PDF, MIME другого семейства) → `unresolved`.
- Пользовательские правила `ClassificationRule`, конвейер «правила → ИИ только для `unresolved`».
- Шаблон папок с названиями из локализации, год по `capturedAt` или `modifiedAt` с настраиваемой функцией года (местное время).
- Разрешение конфликтов имён суффиксами ` (2)`, ` (3)`, всегда без учёта регистра; составные расширения не разрываются.

### Задача 8. `planner`
- План: карантин лишних копий из зон хаоса, перемещения остальных файлов хаоса по шаблону, создание недостающих папок.
- Встроенный валидатор: нет перезаписи, всё внутри источника, файлы берутся только из хаоса и кладутся только в папки шаблона, операции поддерживаются источником, один файл — одна операция, у каждой цели есть родитель. Нарушение — `PlanInvalid`, такой план не выполняется.
- Инварианты 1, 5, 6, 7, 8 — на сценариях и 60 случайных деревьях.

### Задача 9. `executor`
- Журнал `pending` до вызова ФС, результат — после (инвариант 3).
- Перед перемещением сверяются размер и дата; перед карантином дубля полный хеш **пересчитывается** у копии и у оригинала.
- Если папку не удалось создать — всё, что должно было лечь в неё, пропускается; папка, появившаяся после планирования, используется как есть.
- Явная отмена `cancel()` после текущей операции; выполнение не зависит от подписчиков прогресса.

### Задача 10. `undo`
- Откат всей сессии, группы или одной операции в обратном порядке.
- Все конфликты из 4.8: файла нет, файл изменился, место занято (восстановление рядом как `имя (восстановлено).ext`), папки нет (создаётся), карантин очищен.
- Повторная попытка после `revertSkipped`, отмена посреди отката.
- **Инвариант 4** — property-based тест на 120 случайных деревьях: план → выполнение (в том числе со сбоями и отменой) → откат (в том числе сначала по группам) → снимок ФС совпадает с исходным.

### Задача 11. `recovery` + `quarantine`
- Разбор прерванной сессии: каждая операция `pending` становится `done`, `skipped` или `failed` («требует внимания»); сессия закрывается как `failed` и может быть откачена.
- Новый метод порта `findQuarantined` — чтобы найти объект карантина, ссылка на который не успела попасть в журнал.
- Очистка карантина по сроку (по умолчанию 30 дней) с исключениями: системная корзина Android, недоступные источники, невосстановленные сессии, файлы, которые пользователь пытался вернуть.
- Модель `Settings` и порт `SettingsRepository`.
- Property-тест: падение в случайной точке → recovery → откат возвращает исходное дерево, новый план доделывает уборку.

### Задача 12. `workflow`
- `CleanupWorkflow` — конечный автомат для UI: `idle → scanning → analyzing → planReady → executing → completed/cancelled`, откат, плюс состояния `interrupted` (найдена прерванная сессия) и `failed` (не удалось построить план).
- Несколько источников, одобрение групп и операций (папки следуют за перемещениями), отмена на каждом этапе, откат из истории.
- Порт `FileSource.appFolders` — собственные папки адаптера, исключаемые из уборки.

### Задача 13. drift
- Схема SQLite версии 1, семь drift-репозиториев, снимок схемы в `app/drift_schemas/` для будущих тестов миграций.
- Даты — микросекунды UTC, перечисления — по имени, пути — с учётом регистра, сортировка списков — в Dart.
- Все контрактные тесты репозиториев проходят и для in-memory, и для drift; сквозной сценарий `workflow` целиком на SQLite.

### 3.2. Решения, принятые по ходу реализации (все записаны в `core_modules.md`)

**Модель и порты**
- `name` и `extension` у `FileEntry` вычисляются из пути, а не хранятся отдельно.
- План хранит операции в порядке выполнения; группы — производное представление; «пустой план» означает «нет операций» (неразобранные файлы не считаются).
- После `revertSkipped` откат можно повторить; сессию `failed` можно откатить.
- Ошибки хранилища — исключения, ожидаемое «не найдено» — `null`; нарушение правил журнала — `StateError` (ошибка программы).
- Классификатор не возвращает ошибок: при сбое он отдаёт `unresolved`.

**Зоны, дубли, классификация, шаблон**
- Папки проектов исключаются целиком; исключение отдельных файлов (`desktop.ini`, `.crdownload`, `~$…`).
- `Downloads/Telegram Desktop` убирается только сверху: чат-экспорты в подпапках остаются.
- Эвристика «организованности» в этапе 1 не реализована: после решения о подпапках она ни на что не влияет.
- Известные «прочие» типы (`torrent`, `ics`, `vcf`, шрифты) → категория `other`.
- Год по местному времени через параметр `yearOf`.
- Имена всегда сравниваются без учёта регистра при поиске конфликтов.

**Планировщик и выполнение**
- Папки, состояние которых не удалось проверить, план не использует; без `canMkdir` — перемещения только в существующие папки; без карантина и альбома дубли только показываются.
- Перед перемещением хеш не пересчитывается (сверяются размер и дата): перемещение изменившегося файла безопасно, а перечитывать всё дорого. Перед карантином — пересчитывается обязательно.
- `mkdir` уже существующей папки — `skipped`, такая папка при откате не удаляется.

**Восстановление, карантин, откат**
- `recovery` для `move` сначала проверяет исходное место: перемещение атомарно, файл на месте значит «не выполнялось».
- Очищенный карантин отражается как `revertSkipped` с причиной «the quarantine was purged» — так же, как его видит откат.
- Минимальный срок карантина — 1 день.
- Метка «восстановлено» передаётся из локализации.
- Папку, которую пользователь пересоздал после отката, откат повторно не удаляет.

**Workflow и данные**
- Отмена выполнения и отката — явный метод, а не отписка от потока.
- Поток состояний доставляется асинхронно, по порядку; новый подписчик получает текущее состояние.
- Одобрение папок вычисляется из одобрения перемещений.
- Хранение в SQLite: даты — микросекунды UTC, перечисления — по имени (переименование значения — изменение схемы).

## 4. Открытые вопросы — о чём ещё предстоит подумать

### 4.1. До начала этапа 2 (дешевле решить до появления UI)
1. **Тексты причин и ошибок.** `reason` у операций и `error` в журнале — английские строки внутри ядра. Для UI на нескольких языках лучше перейти на типизированные коды (и параметры), а тексты формировать в локализации. Это изменение модели и схемы БД.
2. **Отмена посреди хеширования большого файла.** Сейчас отмена срабатывает между файлами; на многогигабайтных видео это заметно.

### 4.2. Desktop-адаптер (этап 2) — вопросы безопасности
3. **Символические ссылки и junction-точки.** Адаптер не должен идти по ссылкам за пределы источника и попадать в циклы; перемещать нужно саму ссылку, а не цель.
4. **Точки монтирования внутри источника.** Перемещение между разными дисками — это копирование и удаление, а не атомарное переименование. Нужно определять границы томов: считать их отдельными источниками или исключать.
5. **Точность даты изменения** на разных ФС (FAT — 2 секунды, NTFS — 100 нс, ext4 — наносекунды): отпечатки сравниваются точно, адаптер должен отдавать стабильное значение.
6. **Регистр имён:** macOS (APFS по умолчанию) и Windows не различают регистр, Linux различает. Ядро к этому готово; адаптер должен отдавать фактическое написание имени.
7. **Где хранить карантин на desktop:** на том же диске, внутри источника (через `appFolders`), с понятным для пользователя именем; что делать, если источник — корень диска только для чтения.
8. **Заблокированные файлы на Windows**, длинные пути (больше 260 символов), права доступа.

### 4.3. Продукт и UI
9. **Режим «почистить дубли в моих папках»** с отдельным подтверждением (отложен решением по дублям вне хаоса).
10. **Подсказка «эта папка похожа на свалку — убрать?»** вместо эвристики организованности.
11. **Как показывать пользователю** `failed` («требует внимания») после recovery, `revertSkipped` и копии вне хаоса.
12. **Откат старых сессий**, если более новые уборки трогали те же файлы: ядро защищено проверками, но UI должен предупреждать.
13. **Свежесть плана:** если план долго лежит неисполненным, файлы меняются; исполнитель пропустит изменившиеся, но, возможно, стоит предлагать пересканировать.

### 4.4. Производительность
14. Планировщик и зоны работают с полным списком файлов источника в памяти. Для сотен тысяч файлов это нужно измерить на реальных данных (этап 2) и при необходимости перейти на постраничную обработку.

### 4.5. Окружение и процесс
15. **Проект не под git** — работа этапа 1 не защищена от потери.
16. **Нативные сборки не проверялись:** нет Android SDK; для Linux нужны `clang`, `cmake`, `ninja`, GTK.
17. **CI** (format, analyze, test на каждый коммит) не настроен.

### 4.6. Из `architecture.md` (раздел 23), до этапов 4–5
18. Юридическое оформление: на кого регистрировать аккаунты магазинов, LLM-провайдера и платежей.
19. Выбор LLM-провайдера и модели, цена подписки и квоты, desktop-платежи (Stripe или Paddle).

## 5. План следующих шагов

### 5.1. Сразу
1. `git init` и первый коммит всего этапа 1.
2. Flutter в PATH: `export PATH="$HOME/development/flutter/bin:$PATH"` в `~/.bashrc`.
3. CI: GitHub Actions с `dart format --set-exit-if-changed`, `flutter analyze`, `flutter test`.
4. Тулчейн для desktop-сборки: `sudo apt install clang cmake ninja-build libgtk-3-dev` (Linux); Windows — на домашнем ПК.

### 5.4. Дальнейшие этапы (по `architecture.md`, раздел 21)
- **Этап 3 — Android MVP:** Kotlin-слой (`MANAGE_EXTERNAL_STORAGE`, запасные SAF и MediaStore), системная корзина, foreground service; без ИИ.
- **Этап 4 — Бэкенд и ИИ:** Spring Boot, аутентификация, LLM-прокси, квоты, согласие и минимизация данных (GDPR). Облачный `Classifier` подключается в уже готовый `ClassificationPipeline`.
- **Этап 5 — Подписка и публикация:** RevenueCat, Google Play Billing, desktop-платежи, экран Pro; публикация Android и desktop.
- **Этап 6 — iOS:** Swift-слой (PhotoKit, закладки на папки), альбом «На удаление» (порт уже поддерживает), онбординг, IAP; облачная сборка и TestFlight.
