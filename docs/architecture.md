# File Organizer — архитектура приложения

Приложение «одна кнопка»: по нажатию сканирует файлы на устройстве, находит дубли, раскладывает файлы по понятной структуре папок, а при необходимости откатывает всё назад.

Платформы: **Android, iOS, Windows / macOS / Linux**.
Рынок: **весь мир**. Серверы: **Европа**.
Код пишется с помощью Claude Code, поэтому стек выбран по критериям «агент хорошо знает стек и может сам проверить результат».

## 2. Ограничения платформ

### Android
- Полный доступ к общему хранилищу (Downloads, Documents, DCIM, Pictures и т.д.) через разрешение `MANAGE_EXTERNAL_STORAGE` («Доступ ко всем файлам»).
- Google Play выдаёт это разрешение после ручной проверки: управление файлами должно быть основной функцией приложения. Нужна декларация при публикации.
- Запасной режим без этого разрешения:
  - **SAF** (Storage Access Framework): пользователь сам выбирает папки;
  - **MediaStore**: только медиафайлы.
- Данные других приложений (`Android/data`) недоступны.
- Удаление и перемещение чужих медиафайлов требует системного подтверждения.
- Для медиа есть системная корзина (Android 11+) с возможностью программного восстановления.

### iOS
- Приложение работает в песочнице и **не может сканировать всю файловую систему**.
- Доступно:
  - **фото и видео** через PhotoKit (с разрешения пользователя). Основной источник дублей;
  - **папки, выбранные пользователем** в приложении «Файлы». Доступ сохраняется через security-scoped bookmarks;
  - собственная папка приложения.
- Удалённые фото попадают в «Недавно удалённые», и **приложение не может программно вернуть их оттуда**. Поэтому дубли фото не удаляются, а складываются в альбом «На удаление».
- Перед кнопкой нужен онбординг: доступ к фото и выбор папок.

### Desktop (Windows / macOS / Linux)
- Полный доступ к диску через `dart:io`, нативный код не нужен.
- Системные и служебные папки исключаются правилами.
- Объёмы большие (сотни тысяч файлов, терабайты), поэтому инкрементальный индекс обязателен.

                              │ аутентификация · подписки ·     │

Принцип гексагональной архитектуры:
- **Ядро** — домен. Не знает, на какой платформе работает и откуда берётся классификация.
- **`FileSource`** — порт для работы с файлами: список, метаданные, хеш, переместить, в карантин, восстановить, создать папку.
- **`Classifier`** — порт для классификации файлов. Реализации: правила (локально), облачный через бэкенд, заглушка для тестов.
- **Платформенный слой** — адаптеры. Только выполняют команды ОС, бизнес-логики в них нет.

## 6. Взаимодействие Dart ↔ нативный код

Взаимодействие похоже на «React + REST + Spring Boot», только внутри одного процесса и без сети.

- **Запрос–ответ.** Dart вызывает метод и асинхронно ждёт результат, как `fetch`.
- **Поток событий.** Натив шлёт события прогресса (например, при хешировании), как SSE.
- **Pigeon.** Контракт описывается один раз, генерируются Dart-клиент, Kotlin-интерфейс и Swift-протокол. Остаётся реализовать интерфейс на нативной стороне.

Нативная сторона содержит 5–10 методов:
- запросить и проверить разрешения;
- получить список файлов (постранично);
- получить метаданные;
- посчитать хеш (потоково, в нативном коде);
- переместить;
- в карантин / в системную корзину;
- восстановить;
- создать или удалить пустую папку.

Пример одного вызова:
```
Кнопка → провайдер → ScanService (ядро)
       → FileSource.listFiles() → AndroidFileSource (Dart)
       ═══ platform channel ═══
       → FileSourceApiImpl (Kotlin) → Android API
       ← результат возвращается как Future
```

## 7. Пайплайн

```
Scan → Index → Analyze → Plan → Review → Execute → Journal
```

| Этап | Что происходит |
|---|---|
| **Scan** | Обход доступных источников. При повторных запусках обрабатываются только изменённые файлы (по mtime и size) |
| **Index** | Запись метаданных в локальную БД |
| **Analyze** | Поиск дублей, затем классификация правилами, затем облачная LLM для остатка (Pro) |
| **Plan** | Список операций (MOVE, TRASH, MKDIR), у каждой указана причина |
| **Review** | Пользователь видит план, может снять галочки с отдельных операций и групп |
| **Execute** | Выполнение с записью в журнал до и после каждой операции |
| **Journal** | Основа для отката и восстановления после сбоя |

**ИИ не имеет прав на изменение файлов.** Он только участвует в построении плана. Выполняет план детерминированный код на устройстве и только после подтверждения пользователя.

## 8. Поиск дублей

Детерминированно, от дешёвых проверок к дорогим:
1. Группировка по размеру. Файлы уникального размера сразу отсеиваются.
2. Частичный хеш: первые и последние 64 КБ.
3. Полный хеш (xxHash или SHA-256) только для оставшихся кандидатов.

Хеширование выполняется потоково в нативном слое (на desktop — в изоляте). Хеши кешируются в индексе.

**Какой экземпляр оставлять** — по правилам: самый старый, в «правильной» папке, с более осмысленным именем.

**v2:** похожие, но не идентичные фото через перцептивный хеш (pHash).

## 9. Структура папок

### Шаблон верхнего уровня (фиксированный)

```
Документы/
Фото/<год>/
Видео/<год>/
Скриншоты/<год>/
Музыка/
Архивы/
Установщики/
Прочее/
```

Названия папок локализуются под язык системы.

### Почему шаблон фиксированный
- **Предсказуемость:** пользователь заранее знает, где искать файлы.
- **Доверие:** структура не меняется от уборки к уборке.
- **Тестируемость:** шаблон проверяется тестами, свободная генерация — нет.

### Роль ИИ
- Подпапки внутри категорий (например, `Документы/Налоги`, `Документы/Авто`).
- Классификация файлов, которые правила не распознали.

### Что убирается, а что нет
- Убираются **«зоны хаоса»**: Загрузки, Рабочий стол, корень хранилища, папки мессенджеров.
- **Не трогаются папки, которые пользователь организовал сам.** Признаки: осмысленные имена, однородное содержимое, вложенная структура.

## 10. Классификация и ИИ

### Уровни
1. **Правила** (локально, бесплатно, покрывают 80–90% файлов): расширение, MIME-тип, EXIF, источник (скриншоты, мессенджеры, загрузки), шаблоны имён.
2. **Облачная LLM** (Pro) для оставшихся «непонятных» файлов и подпапок внутри категорий. Запросы отправляются пачками через бэкенд.

### Что уходит в облако
- Только метаданные: имя, расширение, размер, дата, относительный путь.
- **Содержимое файлов никогда не отправляется.**
- Перед отправкой метаданные минимизируются (см. раздел 13).

### Почему через свой бэкенд
- API-ключ провайдера нельзя хранить в приложении.
- Промпты и выбор модели меняются на сервере без выпуска новой версии приложения.
- Учёт квот и проверка подписки.
- Возможность сменить LLM-провайдера без изменений в приложении.

### Стоимость
- Отправляются только метаданные (~30–50 токенов на файл), а правила отсеивают большую часть файлов. На недорогой модели это порядка центов за уборку (оценка, проверить по актуальным ценам).
- Расходы контролируются квотами в подписке.

## 11. Бэкенд (Spring Boot, ЕС)

### Ответственность
| Модуль | Что делает |
|---|---|
| Аутентификация | Анонимный аккаунт устройства при первом запуске; опционально вход через Apple / Google, чтобы подписка работала на нескольких устройствах (телефон + ПК) |
| Подписки | Проверка статуса подписки. Источник истины — RevenueCat (вебхуки) |
| Квоты | Лимит запросов к LLM на пользователя в месяц, rate limiting |
| LLM-прокси | Формирование промпта, вызов провайдера, валидация ответа (строгий JSON-формат), повтор при ошибке |
| Конфигурация | Версии промптов, выбор модели, feature-флаги |

### Серверная БД (PostgreSQL)
| Таблица | Назначение |
|---|---|
| `app_user` | Пользователь, способ входа |
| `device` | Устройства пользователя и платформы |
| `entitlement` | Активный уровень доступа (Free / Pro) и срок действия |
| `usage` | Потребление LLM за период (запросы, токены) |

- REST + OpenAPI-спецификация в `api/`.
- Dart-клиент генерируется из спецификации.

### Размещение
- VPS или managed-сервисы у европейского провайдера, PostgreSQL там же.
- HTTPS, ключи провайдера LLM только на сервере.

## 13. Приватность и GDPR

Имена файлов и пути могут содержать персональные данные (например, «Паспорт_Иванов.pdf», `C:\Users\Ivan\...`), поэтому GDPR применяется даже при отправке только метаданных.

- **Явное согласие** перед первой отправкой в облако, с примером того, какие данные уходят.
- **Минимизация данных:**
  - путь обрезается до значимой части; домашний каталог заменяется на `~`;
  - опционально маскируются длинные числа (номера документов, телефоны).
- **Сервер не хранит** метаданные файлов, логи без имён файлов.
- **LLM-провайдер:** договор обработки данных (DPA), режим без хранения и без обучения на данных, по возможности обработка в ЕС.
- **Документы:** политика конфиденциальности, Data Safety (Google Play), App Privacy (App Store).
- Удаление аккаунта и данных по запросу пользователя.

| Таблица | Назначение | Основные поля |
|---|---|---|

## 15. Откат

### Принцип
- Каждая уборка — это сессия, каждое действие записывается в журнал **до** выполнения.
- Удалений нет, только карантин. Без этого откат невозможен.
- Откат — проход по журналу **в обратном порядке** с обратной операцией:
  - перемещение возвращается на место;
  - файл восстанавливается из карантина;
  - созданные приложением папки удаляются, если пусты.

### Надёжность (как WAL / transactional outbox)
1. Записать операцию со статусом `PENDING`.
2. Выполнить её.
3. Обновить статус на `DONE`.

При сбое посреди уборки следующий запуск находит незавершённую сессию и предлагает «Доделать» или «Откатить».

### Проверки перед возвратом каждого файла
| Ситуация | Поведение |
|---|---|
| Файл переместили или удалили вручную | Пропустить, показать в отчёте |
| Файл изменён (другой хеш или mtime) | Спросить пользователя или пропустить |
| На исходном месте уже другой файл | Не перезаписывать, вернуть с суффиксом «(восстановлено)» |
| Исходная папка удалена | Создать заново |
| Карантин очищен | Сообщить, что откат для этих файлов невозможен |

**Главное правило: откат никогда ничего не перезаписывает.**

### Варианты отката
- Вся сессия целиком.
- Частично: по группе (только дубли, только перемещения в определённую папку) или отдельный файл.
- Сначала откатывается последняя сессия (как стек). Более старые тоже можно, но с проверкой конфликтов.

### Карантин по платформам
| Платформа | Реализация |
|---|---|
| Android, медиа | Системная корзина (Android 11+), восстановление программное |
| Android, прочие файлы | Своя папка-карантин |
| iOS, фото | Альбом «На удаление» вместо удаления; откат — удаление альбома |
| iOS, выбранные папки | Папка-карантин внутри выбранного источника |
| Desktop | Своя папка-карантин **на том же диске** (перемещение мгновенное). Системная Корзина не используется |

- Срок хранения карантина — 30 дней (настраивается), потом очистка.
- При перемещении между дисками исходная дата изменения сохраняется явно.

## 16. Фоновая работа и возобновляемость

| Платформа | Поведение |
|---|---|
| Android | Foreground service с уведомлением о прогрессе («Уборка: 45%»); WorkManager для уборки по расписанию (Pro) |
| iOS | Скан выполняется при открытом приложении с прогрессом; фоновые задачи (BGProcessingTask) запускаются только когда решит система, без гарантий |
| Desktop | Ограничений нет |

**Пайплайн возобновляемый.** Прогресс сохраняется в `scan_checkpoint` и журнале. Если процесс прервали, работа продолжается с места остановки.

Тяжёлые вычисления выполняются в изолятах или нативном коде, чтобы не блокировать UI.

## 17. Безопасность и исключения

- Никаких необратимых удалений.
- Исключения по умолчанию:
  - системные папки, Program Files, AppData;
  - папки с кодом (`.git`, `node_modules` и т.п.);
  - папки других приложений;
  - папки, организованные пользователем (см. раздел 9).
- Дубли внутри проектов и архивов не трогаются.
- **Desktop / Windows:** заблокированные файлы пропускаются; поддерживаются длинные пути (>260 символов).
- Пользователь всегда видит план до выполнения.

## 18. Интерфейс

1. **Онбординг:** выдача разрешений; на iOS — выбор папок и доступ к фото; согласие на облачную обработку (для Pro).
2. **Главный экран:** большая кнопка «Навести порядок» и статистика последней уборки.
3. **Прогресс:** этапы пайплайна и счётчики.

5. **Результат:** итог и кнопка «Отменить».
6. **История:** список сессий с кнопкой «Откатить» (целиком или частично).
7. **Подписка:** экран Pro, управление подпиской.
8. **Настройки:** источники, исключения, правила, срок карантина, расписание.

## 19. Тестирование и работа с Claude Code

- **Ядро на чистом Dart** без зависимостей от платформы. Тестируется полностью автономно.
- **Фейковая файловая система** (реализация `FileSource` в памяти): сценарии «1000 файлов, 50 дублей, сбой посреди уборки, откат с конфликтами» проходят за секунды.
- **Заглушка `Classifier`**, чтобы тесты не тратили токены LLM.
- **Нативный слой тонкий**, проверяется интеграционными тестами на эмуляторе и вручную на устройстве.
- **Бэкенд** — обычные тесты Spring Boot; LLM-провайдер подменяется заглушкой.
- **Самопроверка агентом:** `flutter analyze`, `flutter test` и тесты бэкенда после каждого изменения.
- **CLAUDE.md** описывает слои, порты и правило «ядро не импортирует платформенный код».

## 20. Сборка и тестирование под iOS

Решение отложено до этапа 6. До него Mac не нужен.

План:
1. Аккаунт **Apple Developer Program** (платный, ежегодный) — нужен для любой установки на реальный iPhone и публикации.
2. Сборка в облаке: **Codemagic** или **GitHub Actions** с macOS-раннерами.
3. Установка на iPhone через **TestFlight** — Mac для этого не нужен.
4. Тестирование на реальном iPhone (PhotoKit и выбор папок в симуляторе ведут себя иначе).
5. Покупка своего Mac (например, б/у Mac mini на Apple Silicon) — только если iOS-разработка станет регулярной и отладка через облако будет тормозить работу.

## 22. Риски

- **Аккаунты разработчика, LLM API и приём платежей.** Для глобальной публикации нужно заранее решить, на кого регистрируются аккаунты Google Play, Apple Developer, LLM-провайдера и платёжных систем. Для резидента России это может потребовать отдельного решения (например, юрлицо за рубежом) — уточнить у специалиста до этапа 4.
- **Проверка Google Play** для `MANAGE_EXTERNAL_STORAGE`. Описание и UX должны ясно показывать, что управление файлами — основная функция. Запасной режим SAF / MediaStore готовится заранее.
- **iOS сильно ограничен.** Ценность там строится на фото и выбранных папках.
- **Доверие пользователя.** Одна ошибка с потерей файлов убьёт продукт, поэтому карантин, план до выполнения и откат обязательны.
- **GDPR.** Имена файлов — потенциально персональные данные; нужны согласие, минимизация, DPA с провайдером.
- **Экономика подписки.** Стоимость LLM должна укладываться в цену подписки; контроль через квоты и отправку только метаданных.
- **Подпись desktop-сборок.** Без подписи Windows SmartScreen показывает предупреждение, на macOS нужна нотаризация.
