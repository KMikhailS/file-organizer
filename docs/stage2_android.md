## 0. Цель этапа 2

Рабочее Android-приложение: пользователь даёт доступ к файлам, нажимает кнопку, видит план, применяет его и может всё откатить — на реальных файлах телефона.

**Входит в этап:**
- изменения ядра, отложенные с этапа 1 (коды причин и ошибок, расположение источника, отмена хеширования), и первая миграция БД;
- эксперимент: переименование без перезаписи на хранилище Android;
- адаптер `FileSource` для общего хранилища в режиме полного доступа (`MANAGE_EXTERNAL_STORAGE`);
- нативный слой на Kotlin (Pigeon): разрешения, корни хранилища, даты съёмки из MediaStore, foreground service;
- платформенные службы, слой состояния на Riverpod, локализация ru / en;
- UI для телефона: онбординг с разрешениями, главный экран, прогресс, план, результат и откат, история, настройки;
- тесты на эмуляторе (несколько версий Android), ручной чек-лист на телефоне пользователя, сборка APK.

**Не входит в этап:** запасные режимы без полного доступа (SAF, MediaStore) — следующий этап, до публикации в Google Play; SD-карты и USB-накопители; публикация в Google Play и декларация `MANAGE_EXTERNAL_STORAGE`; desktop (этап 3); iOS; ИИ и бэкенд; подписка; уборка по расписанию (WorkManager, Pro).

**Результат этапа:** на эмуляторе и телефоне пользователя проходит полный цикл «онбординг → разрешение → кнопка → план → выполнение → откат»; контрактные тесты `FileSource` проходят против Android-адаптера на реальном хранилище эмулятора (Android 11, 14 и последняя версия); все инварианты ядра сохраняются.

## 2. Принципы этапа

1. **Инварианты ядра не ослабляются.** Адаптер — первый код, который трогает реальные файлы пользователя; любое сомнение — в сторону «не трогать».
2. **Адаптер без бизнес-логики.** Он переводит пути и выполняет вызовы ОС; решения принимает ядро.
3. **Никакой перезаписи на уровне ОС** (A.5): `rename` из `dart:io` и Java запрещён; перемещение — только вызовом, который сам отказывает, если цель занята, или решением, принятым по итогам эксперимента.
4. **Единственное удаление** — `purgeQuarantined`, только внутри папки карантина, по проверенной ссылке.
5. **Всё внутри источника.** `Android/data` и `Android/obb` недоступны и так; ссылки не обходятся.
6. **UI не трогает данные напрямую:** `ui → state → core ← data / platform`; проверяет архитектурный тест.
7. **Уборка переживает сворачивание приложения** (A.7), а падение процесса разбирает `recovery`.

## 3. Изменения ядра и данных (общие для всех платформ)

Все изменения порта и модели — с обновлением `docs/core_modules.md` и контрактных тестов.

### 3.2. Расположение источника
- `Source.location` — непрозрачная строка адаптера: для Android в режиме полного доступа — абсолютный путь к корню тома (позже: URI дерева SAF, закладка iOS).

- `Settings.layoutFolderNames` — названия папок шаблона, фиксируются при первом запуске по языку системы; смена языка интерфейса их не меняет (иначе появится второй комплект папок).

### 3.4. Отмена хеширования
- `partialHash` / `fullHash` получают необязательный `CancelToken` (новый тип в `core/ports`); адаптер проверяет его между блоками чтения и возвращает новый вид ошибки `cancelled`. `DuplicateFinder` передаёт токен, `workflow.cancel()` его взводит.

### 3.5. Миграция БД (схема версии 2)
- Сделано так: причины и ошибки хранятся JSON с кодом в тех же TEXT-колонках (`reason_codec.dart`), `sources.location` — новая колонка; подробности — `core_modules.md`, 7a.

## 4. Эксперимент: переименование без перезаписи (задача 2)

Проверить на эмуляторе (Android 11, 14, последняя версия) и на телефоне пользователя, с выданным «Доступом ко всем файлам», в `/storage/emulated/0`:

1. `renameat2(…, RENAME_NOREPLACE)` через FFI к bionic: успех на свободную цель; `EEXIST` на занятую (файл цели не тронут); поведение при разном регистре имени.
2. `link()` (как возможный запасной путь) — поддерживается ли.
3. `mkdir` через FFI: `EEXIST` для существующей папки.
4. Перемещение через FUSE обновляет MediaStore (галерея видит фото на новом месте, без дубликатов в базе).
5. Чтение файлов и листинг через `dart:io` при полном доступе; скорость листинга большого дерева через FUSE.
6. Чувствительность к регистру имён в `/storage/emulated/0`.

**Выход:** таблица результатов в этом документе (раздел 4.1) и решение A.5. Если `RENAME_NOREPLACE` не поддерживается, варианты на выбор пользователя:
- (а) перемещение через MediaStore для медиафайлов + отказ (`canMove` нет) для остальных;
- (б) «проверить, потом переименовать» с проверкой результата после — с явным письменным принятием окна гонки (единственный «писатель» в папке назначения — само приложение, папки шаблона создаёт оно же);
- (в) другое, если эксперимент его подскажет.

Наблюдения:
- **`RENAME_NOREPLACE` на эмуляторах API 30 и 34 не работает для свободной цели** (`EINVAL`): FUSE-демон MediaProvider этих образов не поддерживает флаги `rename2`. Проверку занятости делает ядро до обращения к демону, поэтому на занятую цель ответ правильный (`EEXIST`) — флаг безопасен, но бесполезен. На API 37 **и на телефоне с API 33** работает полностью. Поддержка зависит не от номера версии Android, а от конкретной прошивки: MediaProvider обновляется отдельно от системы (модуль Mainline), у старых образов эмулятора он старый. Поэтому решение ниже выбирает механизм пробой, а не по версии.
- **Ошибки детерминированы:** `errno` после leaf-вызовов FFI читается стабильно во всех прогонах.
- **`link()` и символические ссылки запрещены** (`EACCES`) — запасной путь через `link` невозможен.
- **Общее хранилище нечувствительно к регистру** (и при поиске, и при создании); в листинге — фактическое написание. Перемещение «только со сменой регистра» невозможно (`EEXIST`). Ядро этапа 1 уже сравнивает пути без учёта регистра везде, где это важно (зоны, папки шаблона, конфликты имён, валидатор; `core_modules.md` 4.2, 4.5, 4.6), и планировщик не создаёт перемещений «только со сменой регистра» — доработка ядра не нужна. Контрактные тесты POSIX-адаптера (задачи 6–7) должны проверить, что `move` на имя, отличающееся только регистром от занятого, даёт `targetExists`.
- **MediaStore:** файлы, созданные через FUSE, попадают в базу после сканирования; перемещение уже проиндексированного фото через FUSE (и `renameat2`, и вариант X2) обновляет строку — без дубликатов. После удаления папки и пересканирования строк не остаётся.
- **Скорость:** листинг 5000 файлов через FUSE — 0,1 с на эмуляторах и 0,2 с на телефоне, `stat` — 0,05–0,5 с; узкое место — запись (создание 5000 файлов 7–38 с), а её приложение почти не делает.
- **Телефон** ведёт себя так же, как эмулятор API 37, во всех проверках; на нём сработает основной путь A.5 (`renameat2`).

### 4.2. Решение A.5

**Подтверждено пользователем 2026-10-05, остаточный риск п. 2 принят письменно.** Прогон на телефоне пользователя (2026-10-06) поведение не опроверг: там работает `renameat2(RENAME_NOREPLACE)`; запасной путь п. 2 нужен для прошивок со старым MediaProvider (как на эмуляторах API 30 и 34).

Перемещение без перезаписи — в два шага, выбор определяет проба возможностей при открытии источника (раздел 5.1), а не номер версии:
1. **`renameat2(RENAME_NOREPLACE)`**, если проба показала, что он работает (API 37, Linux; desktop этапа 3).
2. **Иначе (API 30–34): «резерв имени, затем переименование».** Создать пустой файл на месте цели с `O_CREAT | O_EXCL` (атомарно; занято — `targetExists`, ничего не тронуто), сразу перед переименованием проверить, что заготовка всё ещё пустая и это тот же файл (inode), затем `renameat` без флага поверх своей заготовки.
   - **Остаточный риск (требует явного письменного принятия):** если в доли миллисекунды между резервом и переименованием другое приложение откроет именно этот, только что созданный, пустой файл и начнёт в него писать, его запись будет потеряна. Чужой файл, существовавший до резерва, перезаписан быть не может. Это строго лучше варианта (б) «проверить, потом переименовать».
   - **Сбой процесса между шагами** оставляет пустую заготовку на месте цели. `recovery` распознаёт её (размер 0, операция в журнале `pending`, источник на месте) и убирает в карантин — без удаления.
   - Для папок (папки шаблона) переименование не нужно: их создаёт `mkdir`, который отказывает на занятом имени.
3. Запрет `rename` / `renameat` в тесте исходного кода `lib/platform/` сохраняется; `renameat` без флага разрешается только внутри одной функции «переименовать поверх своей заготовки» — правило теста меняется в задаче 7 точечно.

## 5. Android-адаптер `FileSource`

### 5.1. Общий POSIX-адаптер (`lib/platform/posix/`, Dart)
Тот же код будет desktop-адаптером для Linux и macOS (этап 3).

- **Пути:** корень — `Source.location`; логический путь → реальный: корень + сегменты через `/`; имя — в фактическом написании, которое вернула ОС.

Размер «0» у обычного файла досчитывается чтением (`SizeReader`): на телефоне FUSE минутами отдавал 0 у только что записанных файлов (5.26, находка 1); так же — в листинге и при сверке объекта карантина с описанием.

- **Папки:** `mkdir` через FFI (`mkdir(2)` отказывает, если путь занят; `Directory.create` молча проходит по существующей папке); `removeEmptyDir` через `rmdir(2)`.

### 5.5. План задачи 6 (утверждён пользователем 2026-10-06)

POSIX-адаптер, часть I — `lib/platform/posix/`, класс `PosixFileSource(sourceId, root)`.

**Что показала проверка `dart:io` на хосте** (основа решений ниже):

| Случай | Поведение `dart:io` | Решение |
|---|---|---|
| FIFO, сокет | `Directory.list` отдаёт `File`; `FileStat.type` — `pipe` / `unixDomainSock`; `FileStat.mode` содержит биты типа (`S_IFMT`) | Отсеивать по типу |
| Устройство (`/dev/null`) | `FileStat.type` — `notFound` | Отсеивается само |
| Символическая ссылка | `Link` при `followLinks: false`; `FileSystemEntity.typeSync(..., followLinks: false)` — `link` | Ссылка на файл — молча пропустить; на папку — в `inaccessible` |
| Имя не в UTF-8 | имя с `U+FFFD`, `stat` по нему — `notFound` | Файл пропустить, его папку — в `inaccessible` (листинг неполный); отличать от файла, исчезнувшего во время листинга, по `U+FFFD` |
| `stat` без прав доступа | **возвращает `notFound`, не бросает** | Уточнять FFI `access(path, F_OK)`: `ENOENT` → `notFound`, `EACCES` / `EPERM` → `permissionDenied` |
| Время изменения | микросекунды сохраняются | Приводить к UTC |

**Решения:**
1. **Пути:** реальный путь = корень + логический путь. Файлы за символической ссылкой на папку — не часть источника: `realpath` родителя должен лежать внутри `realpath` корня, иначе `wrongType` (принцип 5: ссылки не обходятся). Для изменяющих операций (задача 7) проверка пересматривается с учётом гонок.
2. **`stat` / `exists`:** без перехода по ссылкам; ссылка, FIFO, сокет — `wrongType` в `stat`; `exists` — `true` для любого объекта на месте имени (в том числе ссылки), так как имя занято.
3. **Листинг:** обход в глубину по одной папке (`Directory.list(followLinks: false)`), дети сортируются по имени (кодовые единицы) — порядок «по сегментам». Страница — до 500 файлов (размер страницы — параметр для тестов). Курсор — последний выданный логический путь (файл или недоступная папка); при возобновлении на каждом уровне пропускаются дети меньше соответствующего сегмента курсора, по равному — спуск. `skipFolder` — до входа в папку. Корень отсутствует или недоступен — ошибка, поток завершается. Пустой источник — ни одной страницы (как у фейка).
4. **Таблица `errno` → `FileErrorKind`** (раздел 5.1) — отдельная функция; `ENOTEMPTY` = 39 на Linux / Android и 66 на macOS (по платформе).
5. **Хеширование:** один долгоживущий рабочий изолят (запускается лениво), асинхронное чтение блоками по 1 МБ, SHA-256 (пакет `crypto`, добавить в зависимости). Полный хеш — `sha256:<hex>`; частичный — `sha256p:<hex>` от `"<размер>:"` + первые 64 КБ + последние 64 КБ (если файл больше 64 КБ) — определение как в `fake_hash.dart`. Отмена: основной изолят по `CancelToken.whenCancelled` шлёт в изолят «отменить запрос N», изолят проверяет флаг между блоками и отвечает `cancelled`. Для тестов — хук «прочитан блок» (изолят сообщает о каждом блоке). `dispose()` (не в порте) закрывает изолят и порты.
6. **Изменение порта:** `CancelToken.whenCancelled` — `Future<void>`, завершается при `cancel()` (сразу, если уже отменён). Обновить `core_modules.md` и тест токена.
7. **Изменяющие методы** (`mkdir`, `move`, `quarantine`, `findQuarantined`, `restore`, `removeEmptyDir`, `purgeQuarantined`, альбом) в задаче 6 возвращают `unsupported`; все флаги `capabilities` выключены, `providesCapturedAt = false`; `appFolders = {.FileOrganizer}`. Включаются в задаче 7 пробой.
8. **Контракт `FileSource`** делится на `fileSourceReadContract` (листинг, `stat` / `exists`, хеши, отмена) и `fileSourceWriteContract` (`mkdir`, `move`, карантин, `removeEmptyDir`, альбом); `fileSourceContract` = оба. `InMemoryFileSource` проходит оба, POSIX-адаптер в задаче 6 — чтение (фикстура на временной папке: файлы через `dart:io`, время — `setLastModifiedSync`).
9. **Тесты POSIX-адаптера** (`test/platform/posix/`, только временные папки хоста): порядок и курсор на дереве с именами `a b`, `a-b`, `a.b`, `a/…`, кириллицей и эмодзи, возобновление с каждой страницы при маленьком размере страницы; ссылки на файл и на папку, битая ссылка, FIFO (`mkfifo` в тесте), сокет, папка с `chmod 000` (в `inaccessible`, `stat` внутри — `permissionDenied`), имя не в UTF-8; файл за ссылкой на папку — `wrongType`; таблица `errno`; известные значения SHA-256 (пустой файл, `abc`), частичный хеш больших файлов с одинаковыми концами; отмена посреди файла 32 МБ (хук блока: отмена на блоке 0, результат `cancelled`, прочитано меньше всех блоков); `dispose`. Мутационная проверка ключевых тестов.
10. **Архитектура:** код только в `lib/platform/posix/`; тест исходного кода `lib/platform/` (нет `rename`, удаления, `Process`, `syscall`) должен проходить; `access` и `realpath` — разрешённые символы libc.

### 5.6. Итоги задачи 6

Код — `lib/platform/posix/`: `PosixFileSource` (порт), `PosixPaths` (пути и проверка ссылок), `PosixLister` (листинг и курсор), `HashWorker` (изолят хеширования), `fileErrorKindOf` (таблица `errno`), `Libc` (FFI: только `access` и `errno`). Зависимость `crypto` добавлена. Тесты: `test/contracts/posix_contracts_test.dart` (контракт чтения, страницы по 500 и по 1), `test/platform/posix/` (листинг, ссылки, особые файлы, права, имена не в UTF-8, хеши, отмена, `errno`); мутационная проверка — 17 поломок, все пойманы.

Решения, принятые по ходу (в пределах плана 5.5):
- **Проверка ссылок строже п. 1:** `realpath` родителя должен *совпадать* с `realpath(корня)/<логический родитель>`, а не просто лежать внутри корня. Иначе ссылка на папку внутри источника открывала бы пути, которых нет в листинге (п. 1: «файлы за ссылкой на папку — не часть источника»). `realpath` сохраняет имена как переданы и заменяет только ссылки, поэтому регистр на Android не мешает; для macOS (этап 3, `realpath` может вернуть фактический регистр) проверку пересмотреть.
- **`EISDIR` → `wrongType`** (в таблице 5.1 его нет; смысл тот же, что у `ENOTDIR`). Путь под файлом (`ENOTDIR` при разборе пути) — `notFound`, как у фейка.
- **Хук блока в пошаговом режиме:** при заданном `onHashBlock` изолят после каждого блока ждёт ответа основного изолята, а запрос отмены уходит раньше ответа — отмена на блоке N детерминированно останавливает чтение до блока N + 1. Без хука изолят не ждёт; отмена приходит сообщением по `whenCancelled`.
- **Корень источника может быть ссылкой** (`/sdcard`): для корня ссылки разрешаются, внутри — нет.
- **Курсор не откатывается назад:** если папка на пути курсора при возобновлении оказалась недоступной (или с именем не в UTF-8), она попадает в `inaccessible`, а курсор страницы остаётся прежним.
- После `dispose()` хеширование возвращает `ioError`; незавершённые вызовы — тоже `ioError`.


### 5.7. План задачи 7 (утверждён пользователем 2026-10-07)

POSIX-адаптер, часть II — изменяющие методы и проба возможностей.

1. **Открытие и проба:** `PosixFileSource.open(...)` создаёт `.FileOrganizer/` с `.nomedia` и проверяет на своих пустых файлах в `.FileOrganizer/probe/`: `renameat2(NOREPLACE)` на свою занятую заготовку обязан дать `EEXIST` (иначе перемещение выключено целиком); на свободное имя — работает → основной путь; `EINVAL` / `ENOSYS` / `EOPNOTSUPP` → проверяется запасной путь (резерв + переименование) → он; иначе, или если `.FileOrganizer` не создаётся, — источник только для чтения. Пробные файлы не удаляются (удаление запрещено), имена переиспользуются. Листинг не показывает `.FileOrganizer` (свои данные адаптера — не файлы пользователя).
2. **Перемещение (A.5):** проверки — источник обычный файл, на пути к обоим путям нет ссылок, `.FileOrganizer` не трогается. Запасной путь: FFI `open(O_CREAT | O_EXCL)` → `statx` по дескриптору (inode заготовки) → сразу перед переименованием `statx` по пути (тот же inode, размер 0, обычный файл) → `renameat` без флага — только в функции `_renameOntoOwnPlaceholder` (тест исходного кода меняется точечно: литерал `renameat` разрешён только в её теле). `statx` одинаков на всех архитектурах Linux / Android (bionic — с API 30).
3. **Неудачное переименование после резерва** (решение пользователя): заготовка, если это всё ещё она, откладывается тем же механизмом в `.FileOrganizer/placeholders/` — без удаления.
4. **Сбой между резервом и переименованием** (решение пользователя): **`recovery` в ядре.** Для `pending`-перемещения, у которого файл ещё на месте источника, а на месте цели пустой файл, изменённый не раньше начала сессии, — в журнал пишется (`pending`, затем выполняется) помещение этого файла в карантин с новым кодом причины `MovePlaceholder(файл)`; откат такую операцию не восстанавливает (заготовки не было в исходном дереве — инвариант 4). `Recovery` получает `IdGenerator`.
5. **`mkdir`** — FFI `mkdir(2)`; **`removeEmptyDir`** — `Directory.delete()` без рекурсии прямо в теле метода; корень — `unsupported`, `.FileOrganizer` — `permissionDenied`.
6. **Карантин** (A.4): `.FileOrganizer/quarantine/<sessionId>/<n>` и описание `<n>.json` (исходный путь, размер, дата изменения, время помещения — через порт `Clock`). Сначала описание создаётся эксклюзивно (резервирует номер), затем перемещается файл: сбой между шагами оставляет описание без объекта — безвредно. `QuarantineRef` = `<sessionId>/<n>`, проверяется по шаблону (иное — `notFound`). `findQuarantined` — по описаниям, объект должен быть на месте и совпадать по размеру. «Осиротевший» объект без описания пропускается при нумерации и очищается по ссылке. `purgeQuarantined` удаляет объект, описание и пустую папку сессии — удаление только в его теле. Описания восстановленных файлов остаются (сотни байт).
7. **Тесты:** контракт записи против POSIX в обоих механизмах (основной и принудительный запасной) и со страницей 1; новый контрактный тест «перемещение на имя, отличающееся только регистром от занятого» (`targetExists` на источниках без учёта регистра; фейк — в обоих режимах, Linux — с учётом); специфика: подменённая заготовка не перезаписана, отложенная заготовка, `.nomedia`, отказ очистки вне карантина, «осиротевший» объект, проба; ядро — `recovery` с заготовкой, откат её не восстанавливает, кодек причины. Мутационная проверка.

Ядро: причина `MovePlaceholder`, `Recovery` с `IdGenerator` убирает заготовку в карантин, `UndoService` её не восстанавливает; кодек причины в `data`. Тест исходного кода: `renameat` разрешён только в теле `_renameOntoOwnPlaceholder`.

Тесты: полный контракт `FileSource` против POSIX (основной механизм; запасной принудительно — часть записи; страница 1 — часть чтения), новый контрактный тест на имена, отличающиеся только регистром (фейк — в обоих режимах); `test/platform/posix/no_replace_mover_test.dart` (оба механизма, «другое приложение» в окне гонки: пишет в заготовку, подменяет её, источник исчезает → заготовка отложена); `posix_changes_test.dart` (проба, в том числе ФС, отвергающая флаг как эмуляторы API 30 / 34, и ФС, игнорирующая флаг; защита `.FileOrganizer`; ссылки; раскладка и нумерация карантина, «осиротевший» объект, описание без объекта, отказ ссылок вне карантина); `recovery` с заготовкой. Мутационная проверка — 33 поломки, пойманы все, кроме одной эквивалентной.

Решения по ходу:
- **Дескриптор заготовки открыт до конца переименования.** Тест показал: если другое приложение удалит заготовку и сразу создаст свой файл, ФС может отдать ему тот же номер inode, и проверка «тот же файл» его не отличит. Пока дескриптор открыт, inode занят и не переиспользуется — подмена ловится всегда.
- **Листинг не показывает `.FileOrganizer`** (в любом регистре); изменяющие методы порта отказывают в нём с `permissionDenied`.
- **Источник без пробы** (корня нет, `.FileOrganizer` — файл или ссылка, папка только для чтения, нет `renameat2` / `statx` — например, macOS до этапа 3) читается, но возможностей не имеет.
- **Откат оставляет заготовку в карантине** (пустой файл с описанием): откат ничего не удаляет, а очистка по сроку берёт только не откаченные операции. Случай редкий (сбой в доли миллисекунды на старых прошивках, затем откат), утечка — пустой файл.
- **Остаточный случай (не покрыт):** сбой процесса *во время отката* в окне запасного механизма оставит пустую заготовку на исходном месте файла; повторный откат вернёт файл как «имя (восстановлено)». Перезаписи и потери данных нет. Откат не журналирует свои шаги, поэтому `recovery` об этом не знает.
- Изменяющие вызовы FFI синхронные (миллисекунды на FUSE) и выполняются в главном изоляте; если на телефоне это заметно — вынести в изолят в задаче 9.

**Находки чек-листа:**
1. **Устаревший размер 0 (исправлено, решение пользователя).** На телефоне (Android 13, MagicOS 7.1) у 2,5–7 % только что записанных файлов — записанных и shell, и приложением через `dart:io` — `stat`, `fstat` и `lseek(SEEK_END)` минутами возвращают размер 0, хотя чтение даёт содержимое, а медиатека знает настоящий размер; другого неверного значения, кроме 0, не встретилось. Отпечаток операции записывался с размером 0; когда кеш обновлялся, откат по правилу безопасности считал файл изменённым и пропускал его: в одном прогоне не вернулись 58 файлов («Уборка отменена частично», файлы целы — сверено по md5). Исправление в адаптере: `lib/platform/posix/file_size.dart` — `SizeReader`: обычный файл, о котором система сказала «0 байт», досчитывается чтением (по-настоящему пустой стоит одного открытия); через него идут `stat`, листинг скана и сверка размера в `findQuarantined`. Ядро и правила безопасности не менялись. Проверено: после исправления в индексе и отпечатках размер 0 только у действительно пустого файла (до — 68–158), откат полный.
2. **Wake lock (добавлен, решение пользователя).** Foreground service сам по себе не держит процессор: без кабеля с выключенным экраном уборка стояла. `CleanupService` держит `PARTIAL_WAKE_LOCK` всё время работы, каждое обновление уведомления продлевает его срок (30 минут без обновлений — отпускается сам), при остановке — отпускается; разрешение `WAKE_LOCK`. Набор `full_cycle` проверяет: во время выполнения блокировка взята, после конца работы (тест делает паузу перед откатом) — отпущена.
3. **MagicOS приостанавливает фоновую работу (зафиксировано, решение пользователя).** На телефоне пользователя уборка без кабеля с выключенным экраном всё равно стояла ~4 минуты — и с wake lock, и без энергосбережения, при том что приложение в белом списке Doze, в корзине «исключено», а в «Запуске приложений» MagicOS — ручное управление с разрешённой работой в фоне. После включения экрана уборка продолжается с того же места; файлам ничего не грозит (журнал). Живая диагностика (adb по Wi-Fi) перенесена в задачу ускорения.
4. **Описания восстановленных файлов остаются в карантине** — ожидаемо (решение задачи 7, 5.8): по одному `N.json` (сотни байт) на файл.
5. **Атрибуты через FUSE и снимки дерева.** Кроме устаревшего mtime на эмуляторе (выше), на телефоне устаревший размер был виден и в снимках, поэтому снимок не содержит размера (содержимое сверяется по md5).

Мутации: хост — 6, 5 пойманы, 1 эквивалентная (лишняя проверка длины в `testStorageRoot` — удалена). Эмулятор API 34, полный цикл — 3, все пойманы: приложение игнорирует тестовый корень (план не появляется — уборка видит настоящее хранилище эмулятора); откат не удаляет созданные папки (дерево отличается); скрипт не нажимает «Домой» (тест ждёт ухода в фон). Исправление размера, хост — 6, все пойманы (без чтения при 0, чтение всегда, падение на нечитаемом файле, обход `SizeReader` в `stat`, в листинге и в `findQuarantined`). Wake lock, эмулятор API 34 — 2, обе пойманы (не берётся; не отпускается — сначала выжила: проверка шла после удаления приложения тестом, перенесена в паузу после уборки).

Решения по ходу:
- «Мало места» проверяется только на эмуляторе: заполнять память телефона пользователя до 50 МБ — риск для других приложений.
- Полный цикл и чек-лист — на английском в тесте (язык зафиксирован), на телефоне — на языке системы (русском).
- Перед выключением эмулятора — `sync`: иначе последние записи (удаление `FileOrganizerTest/` скриптом) могут не попасть в образ диска, папка «возвращается» после загрузки, и скрипты отказываются работать.
- Нагрузочный тест и полный цикл на телефоне держат экран включённым (`stay_on_while_plugged_in`), значение возвращается в конце.
- Release-APK на телефоне только ставится и запускается: без тестового корня он работает с настоящим хранилищем, уборку им на телефоне не делаем.
- Скрипт «мало места» держит 1 ГБ свободным до установки тестового APK (Android не ставит приложения ниже своего порога, до 500 МБ), затем добирает заполнитель до нужного остатка по фактическому свободному месту.

### 5.27. План задачи 17 (утверждён пользователем 2026-10-15)

Задача добавлена решением пользователя (2026-10-14) по итогам нагрузки (5.26): анализ на телефоне — 156 с, выполнение — ~23 мс на операцию.

Новые цели — эти цифры (50 000 файлов). **Решение пользователя (2026-10-15):** дальше нагрузочный тест идёт на 20 000 файлах (`FILES` по умолчанию в `integration_test/load/run_android.sh`): прогон на 50 000 на телефоне занимал около часа; для сравнения на 20 000 нужен свой первый замер.

На телефоне выигрыш выполнения скромнее, а откат не ускорился. Замеры на телефоне шумные: запись тех же 50 000 файлов шла 1619 с (в 5.26 — 626 с) — похоже, медиатека телефона ещё индексировала только что записанные файлы во время замера. **Решение пользователя (2026-10-15):** дальше ускорение не исследуется, код оставлен как есть; отложено — сравнимый замер старого и нового кода в одинаковых условиях на телефоне и разбор того, на что уходит время отката.

**Проверки на устройствах:**

| Набор | API 30 | API 34 | API 37 | Телефон |
|---|---|---|---|---|
| Полный цикл (с wake lock) | пройден | пройден | пройден | — |
| `interrupted` (обрыв посреди пачки, восстановление, откат) | не запущен (см. ниже) | пройден | не запущен | — |
| `cleanup` (UI, отмена) | — | не запущен | — | — |
| Нагрузка | — | пройдена | — | пройдена |

`interrupted` на API 30 и 37 и `cleanup` на API 34 не запускались: первые две попытки прервала аварийная перезагрузка компьютера (на API 30 набор к тому же отказался работать — в `Download` эмулятора остались файлы `fo13_*` от старого прогона набора `cleanup`; скрипт `app/build/api30_interrupted.sh` убирает только их), затем пользователь решил закончить задачу. Логика пачек и восстановления платформонезависима и проверена на хосте (в том числе обрыв на каждой позиции пачки) и `interrupted` на API 34.

**Найдено по ходу:**
- Тест слоя состояния поймал ошибку в новом коде `DuplicateFinder`: после отмены цикл ждал результат файла, который уже не запрашивался (`null`). Исправлено, добавлен тест ядра (отмена во время последнего блока файла).
- Пачки журнала меняют вид прерванной уборки: падение оставляет «начатой» всю пачку; невыполненные операции восстановление отмечает «прервано до выполнения» — они больше не показываются как проблемы (их файлы на месте, «Доделать» их подхватит). Сбой операции внутри пачки, на которой упало приложение, переоценивается по диску (файл на месте — «прервано до выполнения»).
- Компьютер дважды аварийно перезагружался под нагрузкой (мутации; три эмулятора и сборки параллельно) — журнал обрывается без ошибок, температура процессора в простое была 78–82 °C, служба `systemd-resolve` занимала ядро. После этого устройства проверяются по одному с записью температуры; одна мутация (дозапись итогов отката) осталась в коде после первой перезагрузки — найдена сверкой и убрана; резервная копия мутаций теперь в `app/build/`.

Мутации, хост — 18: 16 пойманы (2 — после добавленных тестов: карантин после перемещений идёт отдельно; `updateAll` с одной операцией дважды при разрешённых переходах), 1 эквивалентная (незапрошенный файл после отмены пропускается или обрывает поиск — итог один), 1 эквивалентная устранена удалением лишней проверки повтора id в `DriftOperationJournal.appendAll`.

Решения по ходу (мои): пачками — только перемещения и папки; отмена выполнения — на границе пачки, отмена отката — сразу; итоги отката не пишутся в `finally` (после падения процесса записи нет); «прервано до выполнения» не считается проблемой.

## 11. Архитектурные правила (расширение архитектурного теста)

| Слой | Может импортировать |
|---|---|
| `core` | только Dart SDK (без `dart:io`) и разрешённые чистые пакеты (без изменений) |
| `data` | `core`, drift, sqlite3 (настройки соединения, 5.27) |
| `platform` | `core`, `dart:io`, `dart:ffi`, `dart:isolate`, сгенерированный код Pigeon, разрешённые пакеты платформы |
| `state` | `core`, `data`, `platform`, Riverpod |
| `ui` | `core/model`, `state`, Flutter; **не** `data` и не `platform` |

В POSIX- и Android-адаптерах запрещены `File.rename`, `Directory.rename`, `delete` вне `purgeQuarantined` / `removeEmptyDir` — тест исходного кода `lib/platform/` (`test/architecture/platform_source_test.dart`). Подробнее:
- `rename` / `renameSync` и функции libc `rename`, `renameat` — нигде (перемещение — только механизмом A.5);
- удаление (`delete` / `deleteSync`, libc `unlink`, `unlinkat`, `remove`, `rmdir`, `truncate`, `ftruncate`) — только в теле `purgeQuarantined` / `removeEmptyDir`, только прямым вызовом и никогда рекурсивно;
- `Process` (внешние программы) и `syscall` — нигде: они обходят все проверки выше.

Каждый файл `lib/` принадлежит ровно одному слою (`core`, `data`, `platform`, `state`, `ui`, `l10n`, `main.dart`); файл вне слоёв — ошибка (`test/architecture/layer_dependencies_test.dart`). Уточнения таблицы: `platform` может импортировать из Flutter только `foundation.dart` и `services.dart` (среда выполнения кода Pigeon); `ui` — также `flutter_riverpod`, `flutter_localizations`, `intl` и `l10n`; `l10n` (код `gen-l10n`) — Flutter, `flutter_localizations`, `intl`; `main.dart` — `ui`, `state`, Flutter, Riverpod. Новые пакеты (например, `drift_flutter`) добавляются в белые списки теми задачами, которым они нужны.

## 16. Риски этапа

- **Переименование без перезаписи на FUSE** — главный технический риск; закрывается экспериментом (задача 2) до написания файловых операций.
- **Политика Google Play для `MANAGE_EXTERNAL_STORAGE`:** до публикации нужны запасные режимы и декларация (следующий этап); на этом этапе приложение ставится как APK.
- **Различия производителей** (Xiaomi, Samsung, Huawei): агрессивное энергосбережение может убить сервис — уборка прерывается, `recovery` разбирает журнал; чек-лист на телефоне пользователя.
- **Скорость FUSE** на больших деревьях — нагрузочный тест; при необходимости листинг через MediaStore как ускоритель.
- **Галерея и MediaStore:** перемещения через FUSE обновляют MediaStore, но сторонние галереи могут кешировать миниатюры — проверяется в чек-листе.
- **Ограничение `dataSync` в Android 15** (6 часов в сутки) — для уборки достаточно; обрабатывается отменой.
